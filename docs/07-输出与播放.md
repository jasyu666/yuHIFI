# 输出与播放

> 这份文档回答一个问题：**按下播放之后，数据到底走了哪条路、经过哪些函数。**
>
> 和 `06-HTTP接口.md` 是同一个体例：先把"有哪些路"摆清楚，再给
> **功能 ↔ 入口对照表**，最后是**改这块代码时最容易踩的坑**。
>
> 最后更新：p62（2026-09-23）

---

## 一、两条输出通路

**从 p60 起有两条并列的路，同一次播放只会走其中一条。**

| | **系统音频**（默认） | **USB 直连** |
|---|---|---|
| 实现 | `SystemAudioSink`（AAudio） | `IsoPlayer`（libusb isochronous） |
| 设备 | 蓝牙 / 普通有线 / 扬声器 | 独占小尾巴 |
| bit-perfect | ❌ 经过 AudioFlinger 混音；**走蓝牙还有一层真有损的编码**（SBC/AAC/LDAC） | ✅ |
| 需要小尾巴吗 | **不需要** | 需要 |
| DSD | ❌ **明确拒绝**（要先转有损 PCM） | ✅ 唯一能放 DSD 的路 |
| 速率 | 强制落到 `AudioManager.PROPERTY_OUTPUT_SAMPLE_RATE` | 尽量直通，不行才重采样 |
| 音量 | **系统音量键** | UAC 硬件音量（Feature Unit） |

**为什么默认是系统音频**：这是产品决定 —— 不追求 hifi 时也得能用
（外放、蓝牙耳机、普通有线），不该"没插小尾巴就什么都放不了"。
**它不是权宜之计**，切换开关在 设置 → 输出方式。

## 二、播放链路

```
                       ┌─────────────────── 共用 ───────────────────┐
 文件(fd) ──► AudioEngine::open ──► 解码线程 ──► 重采样(可选) ──► 环形缓冲 2MB
                    │  DSD 分流                （只在这条线程上碰 swr）
                    │  DSD 不走重采样
                    └────────────────────────────────────────────────┐
                                                                     │
                        ┌────────────────────────────────────────────┘
                        ▼
              PcmSource::fill（同一个接口，同一个环形缓冲）
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
   IsoPlayer（USB 线程）        SystemAudioSink（AAudio 回调线程）
   环形缓冲 → URB → DAC         环形缓冲 → AAudio → AudioFlinger → 设备
```

**★ 关键设计：两个输出端消费的是同一个 `PcmSource`。**

`AudioEngine::source()` 返回的就是那个环形缓冲。所以解码线程、环形缓冲、
重采样器、欠载记账**全部共用**，多出来的那条路只是在另一头把 `fill()`
出来的字节交出去。

**★ 线格式也完全一致**：`fill()` 吐的是"声道交织、小端、每样本 `subframeSize`
字节"的整数 PCM，而 AAudio 的 `PCM_I16` / `PCM_I24_PACKED` / `PCM_I32`
正好就是这个布局 —— **一个字节都不用转，也就不会引入任何失真**。

## 三、路由规则（`PlayerSession.playLocked`）

```
                ┌─────────────────────────────┐
                │ DeviceGate.isReady ?        │  否 → 记下 pendingPlay，设备就绪后自动续播
                └──────────────┬──────────────┘
                               │ 是
                ┌──────────────▼──────────────┐
                │ 设置里开了「USB 直连」吗？   │
                └──────┬───────────────┬──────┘
                   开  │               │ 关（默认）
                       ▼               ▼
        sysRate = 0                 sysRate = nativeProbeSystemAudioRate()
        （要 UAC 描述符）             （失败回落 48000）
                       │               │
                       │               ▼
                       │      ┌────────────────────┐
                       │      │ 文件是 DSD 吗？     │──是──► 抛错：
                       │      └────────┬───────────┘        "DSD 不能走系统音频"
                       │               │ 否
                       │               ▼
                       │      nativeStartSystemPlayback()
                       ▼
          挑 alt setting（PCM/DSD 互斥的两条路）
                       ▼
          nativeStartPlayback() → IsoPlayer.start()
```

**决策点只有一处**：`PlayerSession.playLocked` 里算出来的 `sysRate`。
`> 0` 就是系统音频，`== 0` 就是 USB 直连。**没有第二处判断。**

### 三条不变量

1. **DSD ⇒ 必定 `sysRate == 0`**。DSD 是裸位流，AAudio 只吃 PCM，
   要送进去必须先转 PCM，而那是**有损**的（FIR 低通 + 抽取）。
   与其偷偷降质，不如直接拒绝并说清楚。
2. **`nativeSetOutputMode` 必须在 `nativeOpenFile` 之前调**
   （和 `nativeSetDeviceRates` 同一个套路）—— 速率决策发生在 `open()` 里面。
3. **系统速率每次都重新问**。用户可能中途连了蓝牙、换了耳机，
   那个速率是会变的。问一次几毫秒，不值得为省这点钱埋一个变调的坑。

## 四、功能 ↔ 入口 对照表

### Kotlin 侧

| 功能 | 入口 | 说明 |
|---|---|---|
| 起播（路由决策） | `PlayerSession.playLocked` | **唯一的岔路口**，见上 |
| 探测系统采样率 | `NativePlayer.nativeProbeSystemAudioRate()` | 开临时 AAudio 流读回速率再关 |
| 设定输出模式 | `NativePlayer.nativeSetOutputMode(h, sysRate)` | **必须在 openFile 之前** |
| 起播（系统音频） | `NativePlayer.nativeStartSystemPlayback(h)` | 不需要任何 USB 参数 |
| 起播（USB） | `NativePlayer.nativeStartPlayback(h, …)` | 要一整套 alt/端点参数 |
| 暂停/继续 | `PlayerSession.setPaused` → `nativeSetPaused` | 引擎的 `paused_` 让它吐静音 |
| seek | `PlayerSession.seek` → `nativeSeekTo` | 两条路都走引擎，无需分流 |
| 停止 | `PlayerSession.stop*` → `nativeStopPlayback` | **同时停 player 和 sink** |
| 当前在播吗 | `NativePlayer.nativeIsPlaying` | `player.isRunning() \|\| sink.isRunning()` |
| 能不能开播 | `DeviceGate.isReady` | **不再是"设备可用吗"**，见下 |
| 切模式 | `DeviceGate.reopen(ctx) { }` | 重建原生上下文 |
| 首页状态条 | `HomeActivity.renderDevice` | **只当输出方式指示**，不做连接状态报告 |
| 插上时提问 | `DeviceGate.Listener.onAudioDeviceAttached` | 一次性事件，不是状态变更 |
| 提问弹窗 | `HomeActivity.showDirectPrompt` | 插入时自动弹；点状态条也叫得出来 |
| 播放页徽章 | `NowPlayingActivity.renderBadge` | 系统音频**优先判**，不能落到"直通" |

### 原生侧

| 功能 | 入口 | 说明 |
|---|---|---|
| 无设备上下文 | `nativeOpen(-1)` | **fd < 0** 时跳过 libusb，只建引擎 |
| 带设备上下文 | `nativeOpen(fd)` | 老路 |
| 速率决策 | `AudioEngine::open` | 系统音频时把目标速率包成 `DeviceRateCaps` |
| 输出模式 | `AudioEngine::setSystemAudio` | `systemRate_ > 0` 即系统音频 |
| 系统输出 | `SystemAudioSink::start/stop` | AAudio，SHARED 模式 |
| 系统速率探测 | `SystemAudioSink::probeSampleRate` | 静态方法 |
| USB 输出 | `IsoPlayer::start/stop` | 老路 |
| 设备能力上报 | `EngineInfo.IS_SYSTEM_AUDIO` (=15) | 界面据此**不能**显示 bit-perfect |

## 五、`DeviceGate` 的状态模型（p60 起变了）

**`isReady` 的语义不再是"设备可用吗"：**

```kotlin
val isReady: Boolean get() {
    if (PlayerSession.handle == 0L) return false
    return if (Settings.usbDirect(ctx)) deviceAlive else true
    //                                    ↑ 直连要设备   ↑ 系统音频只要引擎
}
```

**模式决定要不要打开小尾巴：**

| 模式 | `drive()` 的行为 | 上下文 |
|---|---|---|
| 系统音频（默认） | **根本不 openDevice** | `nativeOpen(-1)`，无设备 |
| USB 直连 | 老路（权限 → openDevice → 解析描述符） | `nativeOpen(fd)`，带设备 |

**为什么不一边攥着 fd、一边让系统音频用同一个设备** —— 那是没必要冒的风险。
**检测小尾巴照样能做**：靠 `UsbManager.deviceList` + 插拔广播，
**不需要打开它**（`DeviceGate.presentAudioDeviceName`）。

**拔出的处理**：系统音频模式下**不打断播放** —— 那条路本来就不依赖小尾巴。
只有直连模式（或拔出前确实在用 USB）才收尾；收尾后立刻补一个无设备上下文回来
（引擎是必需品，和小尾巴无关）。

## 六、★★ 改这块代码时最容易踩的坑

### 1. `devh` 现在**可能是 nullptr**

这是引入系统音频模式带来的最大变化。以前上下文只有在设备打开成功时才存在，
所有碰 `devh` 的地方都默认它非空。现在有两种上下文，**任何解引用 `devh` 之前
都必须先检查**。

已经修过的两处（都是"恰好没进循环"才没崩）：
- `describeHandle` —— 诊断页步骤②只检查了"句柄非 0"就调它
- `nativeStopPlayback` 释放接口那段（`claimedInterfaces` 在系统音频模式下是空的）

**还有一处要记住**：UAC 硬件音量那组入口（`ensureAcClaimed` 等）
只在诊断页用，而诊断页都先判了 `parsed == null` —— 但那是**调用方的责任**，
不是原生层的保证。

### 2. 速率给错了是**变调**，不是报错

`AAudioStreamBuilder_setSampleRate` 要不到你给的速率时，AAudio 会**自己挑一个**，
而且不报错。引擎是按我们请求的速率重采样过的 —— 实际速率不同就是变调，
听起来只是"怪怪的"，很难判断出是速率不对。

**所以 `SystemAudioSink::start` 里核对 `AAudioStream_getSampleRate`，
不一致就宁可失败**，不静默地播放变调的声音。

### 3. 界面**不能**把系统音频标成 bit-perfect

哪怕引擎报"没重采样"，那也只说明**我们**没重采样 —— 后面的路
（AudioFlinger 混音、蓝牙编码）照样不是无损的。
`renderBadge` 里 `systemAudio` 必须**优先判**。

### 4. 切模式会重建上下文，**当前播放会中断**

这是有意的：一路放着一路换输出端，状态很容易对不上（谁的环形缓冲、
谁的线格式）。要改的话得非常小心。

### 5. `App.kt` 里有一段**开发期临时代码**

无线传输开机自启，标了「成品前删掉」。

## 七、界面上的两条约定

**① 状态条只当"输出方式指示"，不当"设备连接状态"用。**

```
系统音频                      ← 插着小尾巴时右侧多一个「切直连」
USB 直连 · MOONDROP Dawn Pro   ← 直连带型号
未连接 USB 解码器              ← 直连模式下没插时（这条是必须报的，不是状态报告）
连接失败：…  重试
```

★ **刻意不写"非 bit-perfect"** —— 系统音频**本来就是这样**，
天天顶着一句免责声明看只会变成噪音。想知道细节的人去看设置页那段说明。
★ **刻意不写"已连接 XXX"** —— 「已连接」是设备状态的说法，不是输出方式。
★ **直连带型号、系统音频不带**：直连时"哪台设备在独占"是有用信息
（手上有不止一只小尾巴时尤其）；系统音频那条路可能走蓝牙、外放，
报一个 USB 型号反而误导。

**② 插上小尾巴时弹一次「要不要走直连」。**

- 只在**系统音频模式**下弹（已经在直连了就别烦他）
- 只在**刚插上**时弹，**启动时不弹** —— 否则每次开 App 都挨一次，
  而开发期重装频繁，那就成了纯骚扰。插着启动的话，
  点状态条上的「切直连」是同一个对话框
- 实现上是 `DeviceGate.Listener` 里一个**独立的一次性事件**
  （`onAudioDeviceAttached`），不能复用 `onDeviceStateChanged` ——
  那个是"状态变了，重画"，会反复触发，混在一起每次重画都会弹

**③ 起播失败一律弹对话框说明原因。**

★ **不能只写日志。** 除了音乐库页和诊断页，**所有页面的 `onSessionLog`
都是 `Unit`**（首页、正在播放页、专辑页、歌单页、队列页统统忽略）——
只写日志等于"点了歌没反应"。这个项目已经在这上面栽过一次。

★ **用对话框而不是 Toast**：Toast 一闪而过，而"为什么没播"要几行字才说
得清。对话框带「关闭」按钮，由用户决定什么时候收起来。

★ 对话框需要 Activity，所以进程级的 `PlayerSession` 靠 **[Foreground]**
（`Foreground.kt`，进程级前台 Activity 跟踪器）拿当前页面。
拿不到（后台自动连播时失败）才退回 Toast。
★ 这个跟踪器原来长在 `DebugBridge` 里 —— 抽出来了，因为它**不属于调试功能**，
留两份会各自漂移，而"当前是哪个页面"一旦有两个来源就说不清谁对。

### 文案风格（2026-09-23 定的）

**正式、简洁，不用口语。** 按「结论 → 原因 → 怎么办」组织：

```
系统音频模式不支持 DSD 歌曲。

原因：DSD 为 1bit 位流，系统音频仅接受 PCM，输出前须经有损转换，故不提供此方式。

如需播放，请连接 USB 解码器，或在「设置 → 输出方式」中选择「USB 直连」。
```

★ 用户可见的文案**放 `strings.xml`**，不在代码里拼。
★ **不要写 markdown** —— 对话框和 Toast 都不渲染，`**粗体**` 会原样显示星号。

- 提问弹窗**没有「不再提示」** —— 每次都选"用系统音频"的人会被重复问
