# HiFi USB 探针 v0.1-p0

Android HiFi 播放器的 **P0 可行性验证工具**。

目的只有一个：在投入几个月开发之前，先回答两个决定项目生死的问题——

1. **这台手机 + 这个小尾巴，能不能被应用层独占？**（`libusb_wrap_sys_device` 能否接管 fd）
2. **能不能用自己实现的 UAC 协议栈，把音频以 bit-perfect 方式送进 DAC 并出声？**

---

## 实测结论（2026-09-21）

环境：Xiaomi 23013RK75C / Android 15 (API 35) + MOONDROP Dawn Pro (VID:PID = 2FC6:F06A)

| 步骤 | 结果 |
|---|---|
| ② libusb 接管 fd | ✅ **全程不需要 root** |
| ③ 抢占接口（7 个全试） | ✅ 全部成功 |
| ④ BIT_PERFECT | ❌ 预期内失败（需 `MODIFY_AUDIO_ROUTING` 签名级权限） |
| ⑤ 出声 | ✅ 1kHz 正常，2916 个 URB **零失败、零丢包** |

传输质量：48kHz / 2ch / 24bit 下单包恒为 36 字节（= 48000×6÷8000，理论值），
min/max 无抖动，说明 URB 调度干净。

**结论：自研 UAC 驱动路线在这台设备上完全可行。**

### 已解决：SET_CUR 采样率的 wIndex 字节序

UAC2 的 Clock Source 请求里，Entity ID 与 Interface Number 各占 `wIndex` 的一个字节，
**Entity ID 在高位**：

```
wIndex = (ClockID << 8) | 接口号        例：ClockID=5、AC 接口=0 → 0x0500
```

写成 `(接口号 << 8) | ClockID` 会得到 `LIBUSB_ERROR_IO`。注意错误码不是 `PIPE`——
后者才是设备 STALL 拒绝，`IO` 表示请求压根没被设备接受。
该写法与 Linux 内核 `sound/usb/clock.c` 一致。

⚠️ 由于 Dawn Pro 上电默认就是 48kHz，**"设成 48kHz 成功"并不能证明切换能力**，
必须换一个采样率才能验证。工具现已提供采样率选择器。

### 已解决：非整数包长被帧对齐破坏

44100Hz / 2ch / 24bit 时每 microframe 应发 **33.075** 字节，Bresenham 给出 33/34 交替。
但早期版本会把每个包向下对齐到 6 字节的帧边界（33→30，34→30），
实际速率掉到 **40000Hz**，1kHz 测试音变成 907Hz。

修复方式是**取消逐包对齐**：USB 音频本质是连续字节流，设备会跨包重组样本，
逐包凑整既无必要、也会破坏速率精度。样本连续性改由 `fillTone()` 的跨包续传保证
（未发完的尾部字节留到下一包开头）。

`tools/verify_packet_math.py` 会对全部 24 种采样率/位深组合校验字节总数，
并量化该 bug 的影响，可随时重跑。

### ~~该设备只可靠支持 48k 家族~~ —— 这条结论是错的（p19 已推翻）

> **2026-09-22 更正。** 这一节原先写着「只有 48k 家族可用，44.1k 家族一律失真」，
> 并据此把 44.1k 曲库全部重采样。**那是两个错误叠加后被误判成了设备的能力边界。**

**错在哪**

1. **探针速率 40000 / 50000 / 56000 失败**，被归因成"44.1k 家族坏"。
   其实它们失败只是因为**不是标准速率** —— 见下面的机理。
2. **44100 在 P0 早期确实失真**，但那是**逐包帧对齐 bug**
   （33.075 字节被向下对齐到 30 → 实际只有 40000Hz，1kHz 变 907Hz）。
   那个 bug 修好之后没人重测，结论却一直挂着。
   48000 恰好免疫（6 样本 × 6 字节 = 36，本来就在帧边界上），
   所以看起来像"48k 家族正常、其余失真"。

**真正的规则：设备只认那 8 个标准速率；非标准的它默默忽略，继续按上一次设的速率跑。**

判据是**设备自己的 feedback 端点**（见下），不是 `SET_CUR` 回读：

| 请求 | 设备实测 | 每 µframe 样本（标称/实测） | 结果 |
|---|---|---|---|
| 48000 | 48001.0 Hz | 6.0000 / 6.0001 | ✅ 正常 |
| 44100 | 44100.6 Hz | 5.5125 / 5.5126 | ✅ 正常 |
| 88200 | 88201.2 Hz | 11.0250 / 11.0251 | ✅ 正常 |
| 176400 | 176403 Hz | 22.0500 / 22.0504 | ✅ 正常 |
| 352800 | 352808 Hz | 44.1000 / 44.1010 | ✅ 正常 |
| **44000** | **48001.0 Hz** | 5.5000 / **6.0001** | ❌ **设备没换速率** |

**44000 那行是铁证**：请求 44000，feedback 却报 48001Hz、`Fm=6.0001`（正是 48000 的值）
—— 设备压根没换，还停在上一次的 48000 上。而我们按 5.5 样本/µframe 喂、
它按 6.0 消耗，供不上，音高也不对，听感就是"故障"。

#### 输出速率策略（p19 起）

```
8 个标准速率(44.1k/48k/88.2k/96k/176.4k/192k/352.8k/384k) → 原生直通，bit-perfect
其余速率 → 重采样到**最近**的 48k 家族速率
```

界面上有「**信任 44.1k 家族**」开关，默认开。取消则退回旧策略
（只走 48k 家族），行为与 p18 及以前**逐字节一致** —— 留作现场回退。

**实际影响**：44.1k 曲库从"重采样"变成 **bit-perfect**。这比新增任何功能都值钱，
因为它翻倍了 bit-perfect 的覆盖面。

#### 教训：`SET_CUR` 回读查不出任何东西

- 设备对**任何**速率都返回成功
- `GET_CUR` 还会把设定值**原样回读**（请求 44000 也显示「一致 ✓」）
- 系统 `AudioManager` 报的 88200/176400/352800 同样是错的

**唯一能识破它的是 feedback 端点** —— 它报的是设备自己消耗样本的速率，
与主机怎么组包无关。⑧「速率真伪验证」就是干这个的：逐个速率**实际发流**，
读 feedback，报出设备**实际**在跑的速率。

#### 教训：不能相信 UAC 设备宣称的能力

- 设备的 `FORMAT_TYPE_I` 描述符**被截断**，根本没有速率表
- 设备**接受任意 `SET_CUR`**（8/8 全部"接受"并正确回读），但实际跑不了
- 系统 `AudioManager` 报的 `88200/176400/352800` 也是错的

**播放器必须有自己的实测能力表，不能依赖描述符或系统上报。**

### 该设备的 feedback 端点不按规范上报

Dawn Pro 的 Fm 按「每 1ms 帧的样本数」上报（48000Hz 时为 48.0），
而不是 USB 2.0 规范要求的「每 microframe」（应为 6.0），两者差 8 倍。
按规范解读会得出 384008 Hz 这种荒谬结果。

工具现已用标称采样率反推设备用的是哪种单位。实测 `Fm=48.001`
→ 48000.98 Hz → **+20.4 ppm**，属于正常晶振精度。

## P1：真实文件播放

P0 证明的是「能出声」，P1 才是「能放歌」。链路是：

```
[解码线程]                                      [USB 提交线程]
解码(FFmpeg) → 重采样(可选) → 转线格式 → 环形缓冲 → RingBufferSource → IsoPlayer
```

两条线程只通过无锁环形缓冲交汇：解码线程可以慢、可以卡（读文件、解压、
重采样都不实时）；USB 线程绝不能等，缓冲空了就补静音并记账。

### 用法

插上小尾巴 → ①②③ 走完 → 点 **⑦ 选择音频文件并播放**，用系统的文件选择器
挑一个音频文件即可。播放中可暂停、拖进度条，界面实时显示：

```
源 44100Hz / 16bit  →  输出 48000Hz / 24bit  [重采样]
传输: 重采样   缓冲水位: 96%
欠载: 0 字节   缓冲积压: 187392 字节
```

**`欠载` 是判断缓冲够不够的核心指标**，正常播放应始终为 0。持续增长说明解码
跟不上（换歌、慢速存储），听感是断续爆音。

### 文件怎么读进来的

走 SAF（`ACTION_OPEN_DOCUMENT`）而不是路径：scoped storage 下 App 拿不到任意
路径的读权限。选完文件后：

```
ContentResolver.openFileDescriptor(uri) → ParcelFileDescriptor
    → detachFd()  ← 所有权整个交给原生层
    → FFmpegDecoder 用自定义 AVIOContext 从该 fd 读
```

两个容易踩的点：

- 必须用 `detachFd()` 而不是 `getFd()`。后者 ParcelFileDescriptor 仍持有该 fd，
  一旦被 GC 就会在我们还在解码时把 fd 关掉。
- `detachFd()` 之后**不要**再调 `pfd.close()` —— 此时 fd 已不归它管，再关一次
  关掉的就是原生层正在读的那个。

解码器内部统一输出**交错 S32**（16bit 源左移 16、24bit 源左移 8），
输出时按线格式右移回去。只要输出位深 ≥ 源位深，来回移位精确可逆，bit-perfect 不丢。

### 实际采样率由引擎定，设备只能去适配

与 ⑤ 出声测试相反：测试音是从设备能力出发挑一组最稳妥的参数，
而播放文件时**速率由 `rate_policy.h` 决策、线格式由源位深决定**，
设备这边只能去匹配（`ParseResult.selectForPlayback()`）。匹配不上就报错，
不会自作主张换一个速率 —— 那只会让人以为播放正常、实际听到的是错的。

匹配优先级：容器字节数一致 > 位深不低于源位深 > 容器无对齐歧义。

### 已修：周期性地卡顿，而所有计数器都是干净的

**症状**：完整播放时每隔约 60~90 秒卡一次，但报告里 `缓冲欠载` 只有几百字节、
`URB 失败=0`、`包错误=0`、`单包字节 min/max=24/24` 完美。缓冲水位显示 103~106%。

**这是一条重要线索**：数据供给充足、传输零错误，故障却真实存在 ——
说明问题不在我们这一侧的任何计数器覆盖范围内。

**根因：读到了设备的速率反馈，却没用它。**

```
feedback 原始=0x60008  Fm=6.00012   实测速率≈48001 Hz   偏差 +20.3451 ppm
```

设备通过 feedback 端点明确要求「每 microframe 6.00012 个样本」，
而 `packetSizeFor()` 用的是启动时按标称采样率算死的 `scaledSamplesPerUnit_`，
每帧雷打不动发 6.00000。`feedbackLastActual` 在整个文件里只出现在打印语句中。

于是每秒少发 **0.977 个样本**（每秒累积 20.3µs），DAC 内部 FIFO 被慢慢抽干，
见底就断一下。反推卡顿间隔与 FIFO 深度：

| 每秒累积偏差 | DAC FIFO 深度 | 预计卡顿间隔 |
|---|---|---|
| 20.3 µs | 1 ms | 49 秒 |
| 20.3 µs | **1.5 ms** | **74 秒** |
| 20.3 µs | 2 ms | 98 秒 |

实测卡顿间隔 58 / 92 / 88 秒 → 推算 FIFO 深度 **1.2~1.9 ms**，
对 USB DAC 是完全合理的数值。

**这是异步 DAC 存在的全部意义**：设备用 feedback 告诉主机自己的真实消耗速率，
主机必须跟随。不跟随，失步只是时间问题。

**修法**两处：

1. `applyFeedback()` 把反馈值接进速率控制。沿用报告里已有的单位判定
   （规范要求「每 microframe」，但不少 XMOS 固件按「每 1ms 帧」上报，
   两者差 `unitsPerSecond_/1000` 倍），并**限幅 ±1000 ppm** ——
   这台设备对不存在的实体都照答不误，一个跑飞的反馈值会让包长变成天文数字。
2. `packetSizeFor(包序号)` 改成带状态的 `nextPacketBytes()` 累加器。
   原来那个 `floor((n+1)S) - floor(nS)` 公式**要求速率恒定**，
   速率一旦中途变化，包序号与累计样本数就会对不上。

修好后 `单包字节 min/max` 会从 `24/24` 变成 `24/28` —— 每约 8000 个包多出
一个样本，这正是 +20 ppm 该有的样子。

**实测确认（2026-09-21）**：卡顿消失。三项独立证据：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `单包字节 min/max` | 24 / 24 | **24 / 28** |
| `已送音频时长` | 340.338 秒（短 0.09 秒） | **340.42 秒**（源 340.427） |
| `缓冲欠载` | 111208 字节 | **116 字节**，仅末尾 1 次边界填充 |

```
URB 完成=340414  URB 失败=0  包错误=0  停止时取消=6（正常，不算失败）
```

报告里的自适应状态记录**下发偏差的范围**而不只是最后一个采样点 ——
实测那次末次读到的是整数 6.0（+0 ppm），而同一轮里包长出现过 28 字节，
两者矛盾；只记末次值根本判断不出设备是稳定在标称还是持续在 +20 ppm 附近波动：

```
速率自适应: 已生效 339872 次
  下发偏差 -8 ~ +24 ppm，平均 +19.3 ppm（有波动）
```

### 已修：切屏导致解码线程被冻结

卡顿根因修掉之后，报告里仍留了一条真实欠载：

```
#1  第 63.7152 秒   补静音 3456 字节 ≈ 18 ms
```

用户提供了一个关键观察：**切屏返回时会出现短暂停滞**。这把方向从"存储 I/O 卡顿"
转向了**线程调度**。核对代码：**从未设置过任何线程优先级，也没有前台服务。**

按缓冲深度反推停摆时长：

```
缓冲目标水位 192,000 字节 = 1.0 秒（48k/2ch/2B）
出现 18ms 静音  →  解码线程被饿死约 1.018 秒
```

**一秒多的调度延迟**，不是"优先级低一点"，是被整个挂起了。

#### 结构性原因：系统不知道我们在放音

**因为我们完全绕开了 AudioFlinger，Android 根本看不出这个 App 在播放音频。**
系统判断"是否在放音"靠的是 AudioTrack / AudioService 的活动记录 ——
而我们的数据从 FFmpeg 直接流向 libusb，系统眼里这个进程什么都没干，
于是在切屏后被当作**缓存进程**，Android 12+ 的 **App Freezer 会直接冻结
整个进程的所有线程**。

这是独占路线的一个隐蔽代价：**你越彻底地绕开系统音频栈，系统就越不认识你在放音。**

修法两层：

1. **提升音频线程优先级**（`thread_priority.h`）：
   USB 提交线程 → `URGENT_AUDIO(-19)`，解码线程 → `AUDIO(-16)`。
   漏一个 microframe 就是一声爆音且补不回来，USB 线程必须最高。
   提权失败只记日志、不中断播放 —— 不能因为提权失败就让播放起不来。
2. **前台服务**（`PlaybackService`，`foregroundServiceType="mediaPlayback"`）：
   播放期间常驻，明确告诉系统"这个进程在干活，别冻结"。
   服务本身不做任何播放工作，播放全在原生层，它只是一份声明。

   > 这也是本 App 唯一需要的运行时权限（API 33+ 的 `POST_NOTIFICATIONS`）。
   > 被拒绝**不影响防冻结效果**，只是那条常驻通知不显示 —— 所以是尽力索取，
   > 不阻塞播放，也不拿它当播放的前提。

   **启动失败必须主动收掉自己。** 通过 `startForegroundService()` 启动的服务若没能在
   约 5 秒内调成 `startForeground()`，系统会抛
   `ForegroundServiceDidNotStartInTimeException` 把**整个 App 干掉**。
   所以 `startForegroundCompat()` 用 try/catch 包住，失败时记日志、回传原因并
   `stopSelf()` —— 两害相权取其轻：丢的是防冻结保护，不是 App。

   启动结果会以广播回传，写进导出的报告：

   ```
   前台服务: ✓ 已生效 —— 已进入前台状态，进程不会被冻结
   ```

   失败时还会附上排查提示（含小米/HyperOS 的省电策略）。**防冻结有没有真的生效
   不该靠猜**，它直接决定切屏后会不会出现静音。

   > ⚠️ **小米 / HyperOS 还有一层自己的后台管理**（省电策略、后台弹出、自启动），
   > 那一层**不看标准的前台服务状态**，可以直接限制甚至杀掉后台活动。
   > 如果这里显示"✓ 已生效"但切屏后仍然停顿，去
   > 设置 → 应用管理 → HiFiProbe → 省电策略，改成「无限制」。

### 已排除：wakelock（屏幕并没有关）

"切屏后卡顿"最初怀疑是 **CPU 挂起**：Android 的音频栈在放音时会自动持有
`PARTIAL_WAKE_LOCK`（这就是普通音乐 App 息屏后还能继续放的原因），而我们绕开了
AudioFlinger，没人替我们持有 wakelock。

实测否定了这条路径 —— 用户的操作是**回主页，屏幕全程亮着**：

```
mWakefulness=Awake                     全程
mHoldingDisplaySuspendBlocker=true     ← 屏幕挡着，CPU 根本不会挂起
hifiprobe_wakelocks=0                  我们确实没申请过（但这次无关紧要）
```

**屏幕不关，CPU 就不挂起**，所以 wakelock 不是这个场景的原因。
（如果将来要支持真正的息屏播放，wakelock 仍然是必须补的。）

### 已结案：卡顿 —— USB 提交线程被调度挂起，在途队列太浅

**这是整个排查里唯一一个"先预测、后证实"的修法**，前面每一条假设都是被推翻的。

#### 定位过程

所有常规计数器都干净（零欠载、零 URB 失败、零包错误、wakelock 已持有、
前台服务已生效、优先级已生效、后台 7 核），却依然有可闻的断音。

新增两个指标后真相才出来：

```
已送音频时长≈73.246 秒
实际耗时≈73.299 秒
→ 缺口 0.053 秒      ← 设备累计没收到数据的时长（就是听到的静音）

提交间隔: 最大 24.766 ms（正常 1ms）  超过 4ms: 107 次，超过 8ms: 14 次
```

- **`缺口`** 说明结果：一共少送了多少
- **`提交间隔`** 说明原因：USB 提交线程被调度器挂起了 **16~25 ms**

只统计「超过 4ms / 8ms」后来被证明**不够用**：队列有 32ms 余量，
一个 20ms 的卡顿完全被吸收、听不出任何问题；只有**超过余量**的那部分才会变成断音。
所以现在按**穿透**统计，并把最严重的几次连**时刻**一起记下来：

```
提交间隔: 最大 58.2 ms（正常 1ms，队列余量 32 ms）
  超过 4ms: 47 次，超过 8ms: 12 次
  穿透队列: 1 次，累计断供 26 ms   ← 这个数直接对应听到的静音
  最严重的几次（带时刻，便于和听感对上）:
    #1  第 41.2 秒   卡 58.2 ms   穿透 26.2 ms  ← 这条造成了断音
    #2  第 12.8 秒   卡 19.1 ms   （被队列吸收）
```

**「时刻」这一栏是为对齐听感加的**：只说"最大 691ms"无法和用户说的"中间卡了一下"
对上，必须知道它发生在第几秒。

队列只有 `urbCount = 8` 个 = **8 ms 余量**，扛不住 16~25ms 的挂起 —— 队列一耗尽，
设备就断粮。而这时 `fill()` 根本没被调用，所以**既不欠载也不报错**，
故障发生在"没提交"这个动作的缺席上。

#### 两个被排除的干扰项

- **反馈跟随不是元凶**：A/B 实测跟随开 / 关的卡顿次数几乎相同（105 vs 107）
- **不是 CPU 配额问题**：前台服务把进程保在 `foreground` cpuset（7 核）

#### 修法与验证

`urbCount` 8 → **64**（余量 8ms → **64ms**）。思路是**不跟调度器较劲**——
线程实测就是会被挂起，那就让播放对延迟免疫。

**验证结果（2026-09-22，完整播完一首 340 秒）**：

| | 修改前 | 修改后 |
|---|---|---|
| 最大提交间隔 | 16.1 / 24.8 ms | **20.4 ms（没改善）** |
| >8ms 次数 | 14 / 17 | **17（没改善）** |
| **缺口** | 53 / 63 ms（73s 内） | **3 ms（340s 内）** |
| 缺口率 | 0.72 ~ 1.21 ms/秒 | **0.0088 ms/秒** |

**卡顿照旧发生，缺口却消失了** —— 这恰恰证明机制成立：我们没有消除调度挂起，
只是让它不再造成断粮。如果卡顿次数也一并减少，反而无法排除"系统恰好不忙"这种解释。

其余指标：`URB 失败=0`、`包错误=0`、`差额 0 帧`、`停止时取消=62`（对应 64 个在途 URB，
分类为正常而非失败）。

#### 实测验证（2026-09-22，48k/24bit 直通文件）

用户实测确认**断音与咔哒声都消失**。两份报告：

```
队列深度=32 URB（余量 32 ms）   seek 清队=关   feedback 跟随=开
已送音频时长≈94.3597 秒   实际耗时≈94.369 秒
→ 缺口 0.011 秒（设备全程都在收数据，没有断供）

提交间隔: 最大 21.028 ms（队列余量 32 ms）
  穿透队列: 0 次 —— 所有卡顿都被队列吸收了，没有造成断音
  最严重的几次（带时刻，便于和听感对上）:
    #1  第 11.628 秒   卡 21.028 ms   （被队列吸收）
    #2  第 20.569 秒   卡 19.245 ms   （被队列吸收）
    ...

暂停静音=672780 字节 ≈ 2.33604 秒（暂停期间输出，不计入欠载）
解码器交出: 4420038 源帧  /  写入缓冲: 4420038 输出帧
```

第二份里用户还试了 `seek 清队=开`、暂停 3 次共 22 秒、多次 seek —— **穿透依然 0 次，
缺口 24ms，帧数依然严格相等**。

两个副产品：

- **直通路径（48k 家族，不建重采样器）首次被真实文件验证**：`解码器交出 == 写入缓冲`
  严格相等，帧级完整。这条分支此前从没被跑过（测试文件都是 44.1k）。
- **24bit / 3 字节子帧（alt 2）也首次验证**：`单包字节 min/max=36 / 42`，
  完全符合 24bit×2ch 的预期（6 字节/帧，6 样本=36、偶尔 7 样本=42）。

**注意余量**：实测最大卡顿 21ms vs 队列 32ms，只有 1.5 倍。系统变忙时可能不够 ——
界面上五档可调就是为这种情况留的，听到卡顿就往上调一档，不必重新编译。

#### 默认值与可调范围

实测能消除断音的**最小值是 32 个 URB**（16 及以下会卡）。默认取 **32** 而不是更大，
因为 seek 后旧音频的尾巴长度**等于**队列深度 —— 够用就好。

界面上保留 `8 / 16 / 32 / 64 / 128` 备选，**将来换设备或系统负载变重导致卡顿
超过余量时可以现场往上调，不必重新编译**。8 那一档留着是为了能随时复现旧版
的卡顿做对照。

#### 两个相关开关

**`seek 清队`（默认关）**：seek 时立即取消在途 URB，去掉旧音频尾巴。

- 关（默认）：seek 后最多还有 `队列深度` 毫秒的旧音频放完
- 开：旧声音立刻消失，代价是重填时环形缓冲可能还没灌上，会有一小段静音

实现上是在 `seekToMs()` **返回之后**才清队 —— 它返回时解码线程已经清空并重建了
环形缓冲，此时取消，回调才会用新数据重填。顺序反了就等于白清。

**暂停：送静音，而不是停流**

暂停只停解码线程是不够的 —— 环形缓冲里那一秒还会照常放完，按了暂停要等一秒才静音。

但**把流整个停掉也不对**：DAC 在那段时间收不到任何数据会失去时钟锁定，
恢复时要重新锁定，**那一声就是听得见的咔哒**。（实测踩过：暂停 691ms，
恢复后用户听到了异响。）

正确做法是两者兼得 —— **流继续跑，但只送静音**：

| | 停流（错） | 送静音（对） |
|---|---|---|
| DAC 收到 | 什么都没有 | 连续的 0 |
| 时钟 | 失锁，恢复要重锁 → 咔哒 | 保持锁定 |
| 歌曲位置 | 不前进 | 不前进 |
| 环形缓冲 | 不动 | 不动（**只是不再消费**） |
| 声音 | 立刻停 | 立刻停 |

实现上就是数据源多一条分支：暂停时 `fill()` **整块写 0 并直接返回，完全不碰环形缓冲**。
音频原地冻结，恢复时从断点接着放，一个样本不差。代价是恢复后最多还有「一个队列深度」
的静音已经排在路上（32ms，听不出来）。

"立刻静音"则靠取消在途 URB 实现 —— 那几个里面装的是真实音频，取消掉声音就断了。

### 在查：后台被降级到 3 个 CPU

改用 adb 直接观测进程状态，发现了这条线索：

```
系统共 8 个核（0-7）          大核 cpu7 最高 2.995 GHz
cpuset 分组：
  top-app          0-7         ← 应用在前台时
  foreground       0-2,4-7
  background       0-2         ← 只剩 3 个核
  system-background 0-3

HiFiProbe 进程（非播放时）：Cpus_allowed_list = 0-2，cgroup = /background
```

**应用一旦离开前台，进程就被限制到 3 个核上。**

这条线索之所以重要，是因为它能解释"零欠载却有卡顿"这个矛盾签名：

- **缓冲有 1 秒深**，解码线程被延迟几百毫秒也不会欠载 → 解码侧看不出问题
- **DAC 内部 FIFO 只有约 1.5 ms 深**（由卡顿间隔反推），而 USB 提交线程被延迟时
  `fill()` 根本不会被调用 —— 于是**既不计数也不报错**，只是设备那边断粮了
- nice=-19 只影响 CFS 权重，**不是实时调度**，在少数慢核上仍可能被延迟数毫秒

现在的观测方式是让 **app 自己读 `/proc/self`** 并写进报告 —— 读自己不需要权限，
也不需要 adb 同时在旁边配合：

```
CPU 分组: top-app=0-7  foreground=0-2,4-7  background=0-2
起播时 CPU 配额: cpuset=/top-app  cpus=0-7
⏸ 离开应用   播放位置 0:32   cpuset=/background  cpus=0-2
▶ 回到前台   播放位置 1:18   cpuset=/top-app  cpus=0-7
```

**待确认**：播放期间前台服务是否能把进程保在 `top-app`/`foreground`。
若离开前台后仍掉进 `background`，则根因坐实。

届时的修法方向是**加深在途 URB 队列**（现在 8 个 URB = 8ms 余量，加到 30~60ms），
而**不是跟系统调度对抗** —— 让播放对调度延迟免疫，即使被限制到少数核心，
只要单次延迟不超过队列深度就不会断粮。

### 已修：欠载被记了两份账

欠载有两个计数器：`RingBufferSource` 里的（按是否暂停正确分类）和
`IsoPlayer::prepareTransfer` 里的（`if (valid < offset) ...`，**不知道暂停这回事**）。
报告那行读的是后者，于是暂停静音被重复计了一遍：

```
515,164（暂停静音） + 3,456 + 164 = 518,784  =  报告的"缓冲欠载"值
```

**分毫不差。** 同一件事记两份账，必然有一天对不上。现在欠载/暂停静音统一由
数据源负责（只有它知道补了多少、当时是否暂停），`IsoPlayer` 不再自己记。

### 诊断：提权是否真的成功，报告里必须能看到

`setpriority` 提负 nice 值需要权限（RLIMIT_NICE），**失败是静默的** ——
我们刻意不因提权失败就中断播放，但那样一来失败就完全不可见，排查时会陷入
「明明加了提优先级却还是卡」的假胡同，而真相是压根没提上去。

所以 `thread_priority.h` 不只设一次就完事，还会**回读实际值**并留给报告：

```
── 音频线程优先级 ──
  USB 提交线程: 请求 -19 → 生效
  解码线程: 请求 -16 → **失败**（Operation not permitted），仍为默认优先级
```

（`getpriority` 出错和合法值都可能返回 -1，所以只能靠 `errno` 区分。）

### 诊断：切后台/回前台事件

```
⏸ 离开应用   播放位置 1:03
▶ 回到前台   播放位置 1:05
```

**位置这个数就是对齐用的**：欠载事件也按「第几秒」报，两边一比就能看出卡顿
发生在**离开期间**（进程被冻结）还是**回来那一刻**（Activity 恢复的开销压住了
音频线程）。这两种机制要查的方向完全不同。

### 诊断：欠载事件附带"断供前等待时长"

缓冲耗尽只说"没数据了"，但**是供给方停了多久**才决定了这是调度问题还是别的：

```
欠载事件: 1 次
  #1  第 63.7152 秒   补静音 3456 字节 ≈ 18 ms   断供前已等待 1018 ms   [起播后 63.8 秒]
```

`断供前已等待` 很大 → 解码线程被挂起；很小 → 别的环节（例如 URB 提交）出了问题。
两者要查的方向完全不同。

方括号里的**会话时钟**（距本段开播多久）是单调递增的，而「第几秒」在 seek 之后
会跳变 —— 有了它，就能把卡顿精确定位到「回到前台之后第几秒」。

### 已修：暂停静音被记成欠载

暂停只停了**解码线程**，USB 流照跑。缓冲抽干后必然开始补静音 ——
那是**故意的**，却全被记进了欠载：

```
#3  第 317.977 秒   补静音 10483980 字节 ≈ 54604.1 ms
```

暂停 54 秒 → 报告显示"欠载 54 秒"，把唯一的供给健康指标彻底污染。

现在由数据源负责分类（谁补的静音谁记账）：暂停期间的静音单独计，
不进 `underrunBytes`，也不记事件。报告里单列一行
`暂停静音=... 字节 ≈ ... 秒（暂停期间输出，不计入欠载）`。

### 已修：seek 之后记账错乱

两处，都是同一类问题 —— 分段统计被当成累计统计读：

- **差额**：`decodedFrames_` 跨 seek 累加，而 `writtenFrames_` 在 seek 时清零，
  两者相减毫无意义（实测报出 `-16340496 帧 / -340427 ms`）。
  现在 `decodedFrames_` 也在 seek 时清零，是**分段**值，报告里会注明
  「seek 过 N 次，以下为最后一次 seek 之后的分段值」。
- **欠载事件位置**：事件里的帧计数自「记录那一刻的 seek 基准」起算，
  若拿最后一次 seek 的基准去解读所有历史事件，位置会全部错乱
  （实测 340 秒的歌报出"第 634 秒"）。现在每个事件把当时的基准一并记下。

### 音量：系统音量够不着，必须走 DAC 硬件音量

独占路线的直接后果，实测确认：**按手机音量键对响度毫无影响**。

因为我们的采样点从不经过 AudioFlinger —— 通路是
`FFmpeg → 重采样 → 环形缓冲 → libusb URB → DAC`，而系统媒体音量是
AudioFlinger 在混音时施加的软件增益。这是 bit-perfect 换来的代价。

所以音量只能走 **UAC 硬件音量**（Feature Unit），这也正是 HiFi 播放器的标准做法：
DAC 收到满分辨率数据后自行衰减，不牺牲有效位；软件增益则是拿有效位换响度。

请求格式（UAC1/UAC2 一致）：

```
bmRequestType = 0x21 / 0xA1     (class, interface)
bRequest      = 0x01 SET_CUR / 0x81 GET_CUR / 0x82 MIN / 0x83 MAX / 0x84 RES
wValue        = (0x02 << 8) | 通道号      0x02 = CS_VOLUME_CONTROL，通道 0 = master
wIndex        = 实体 ID 与接口号          ← 唯一的未知数，见下
数据          = 2 字节有符号，单位 1/256 dB
```

`wIndex` 的构造与 Clock Source 是**同一类坑**：规范说 Entity ID 在高位，但固件实现
不一致，失败时只给一个语焉不详的 `LIBUSB_ERROR_IO`。所以沿用探针里验证过的做法 ——
不猜，几种组合都试一遍（`(UnitID<<8)|接口`、`(接口<<8)|UnitID`、仅 `UnitID`），
哪个成功用哪个，然后缓存起来（拖滑条时不该每次重试）。

**通道号也一起试**（`CN=0` master / `1` / `2` 逐声道）。这台设备的描述符里
master 明确声明了音量能力（`bmaControls[0]=0x0F`）却实测不响应；
有些设备恰恰相反，只在逐声道上真正实现。多试两组成本极低，漏掉才是损失。

候选会**去重**：AC 接口号为 0 时，后两种 wIndex 构造算出来是同一个值，
不去重会做两遍无用功，报告里还会出现两段一模一样的输出，看着像设备重复作答。

三种全失败时会如实报告「该设备 Feature Unit 不接受音量请求」，
而不是假装可用 —— 那说明它的音量做在模拟域，只能用它自己的按键。

**候选 wIndex 必须通过自洽性检查才算数**，不能只看「GET_CUR 有响应」——
这台设备对不存在的实体也照答不误（P0 阶段用非法实体 `0x7F` 发 GET_CUR 都能成功），
所以「有响应」根本不能证明 wIndex 指对了地方。合格条件是：

```
max > min          ← 区间非空
cur ∈ [min, max]   ← 当前值落在自己声明的范围内
```

这条不是洁癖，是实测崩出来的：探测"成功"拿到一组 `min=1 / max=0` 的垃圾值，
音量键把它喂给 `coerceIn` 直接抛 `IllegalArgumentException` 闪退。
`coerceIn` 在 `lo > hi` 时会抛异常，所以音量路径上一律改用自己写的 `clamp()`
（越界就夹住，非法区间也能容忍），并且在 Kotlin 侧再兜一次 ——
即使原生层给了非法范围，最坏也只是音量不可用，不会崩。

#### 实测结论：这台设备不支持主机侧硬件音量

`nativeVolumeProbe` 把所有 wIndex × 通道组合的原始响应全打出来之后，答案很干脆：

```
wIndex=0x0300（UnitID<<8 | AC接口）  CN=0 master    → CUR=0 MIN=1 MAX=0 RES=0
wIndex=0x0300                        CN=1 逐声道    → CUR=0 MIN=1 MAX=0 RES=0
wIndex=0x0300                        CN=2 逐声道    → CUR=0 MIN=1 MAX=0 RES=0
wIndex=0x0003（AC接口<<8 | UnitID）  全部 CN        → LIBUSB_ERROR_IO
```

三条信息：

1. **`0x0300` 才是正确寻址** —— 实体 ID 在高位，与 Clock Source 一致；
   `0x0003` 被 `LIBUSB_ERROR_IO` 直接拒掉。**我们的寻址没有错。**
2. **三个通道号返回的字节完全相同。** 设备根本没在看请求里的 CN，
   只给一个固定答复 —— 这不是"某个通道没实现"，是整个控制没实现。
3. 返回的是一组**退化范围**：`min=1 / max=0 / res=0`，区间宽度为零。

结合描述符里 master 明确声明了 Volume 支持（`bmaControls[0]=0x0F`），结论是：
**固件声明了音量能力，却没有真正实现该控制请求。**

代码按"能力探测"保留着：能用的设备会自动启用，这台会一直显示"不可用"。

**这意味着：独占模式下，这台小尾巴的音量无法从手机侧调节。**
对播放器来说是个产品层面的取舍 —— 要么不做音量，要么提供会牺牲 bit-perfect
的软件音量（那是拿有效位换响度）。

**音量控件只在播放会话内启用。** 查询音量要 claim 住 AudioControl 接口，
而 ③ 的抢占测试会逐个接口去 claim，两边撞上会让 ③ 的报告出现一条误导性的
「接口 0 抢占失败」。播放时 AC 本来就由原生层合法持有，把音量限制在播放中
既不干扰诊断流程，也正好是真正需要它的时刻。

播放中可以直接按手机音量键调节 —— `onKeyDown` 会把它转成 UAC 请求并吃掉事件，
免得系统再弹一个对这个 App 毫无作用的音量条。

### 播放中 seek：两个必须绕开的线程安全问题

拖进度条时**不能**在调用方线程直接 `av_seek_frame` / `swr_init` ——
解码线程此刻正拿着这两个对象，两者都不是线程安全的，会直接崩。

所以 `seekToMs()` 只登记请求，真正的 seek 由解码线程在循环开头落地。
因此它的返回值语义是「请求已受理」，不代表位置已经变了（正常几十毫秒内生效）。

顺带牵出环形缓冲的一个隐患：`RingBuffer::clear()` 原本注明「仅在两端都停止后调用」，
而 seek 恰好要在消费者运行时清空它。若消费者在这期间提交 `tail_`，
`tail_` 会越过 `head_`，之后所有 `available()`/`space()` 按无符号下溢算出天文数字。
现在 `read()` 改用 CAS 提交，失败即丢弃该批数据并返回 0（由上层补静音）。

### 已修：收尾静音被记成欠载，重采样尾巴没吐出来

实测放完一整首 340.4 秒的 FLAC（44.1k→48k 重采样）后，报告是这样的：

```
URB 完成=340905  URB 失败=0  包错误=0
单包字节 min/max=24 / 24
已送音频时长≈340.905 秒
缓冲欠载(underrun)=111208 字节 ≈ 579.208 ms
```

传输层完美（34 万个 URB 零失败，包长恒定 24 字节），但 `欠载 579ms` 看着像
解码跟不上 —— 而我恰恰把这个指标写成了「判断缓冲够不够的核心依据」。追下去发现
它由两个独立的问题叠加而成。

**其一：收尾时还在喂静音。** 播放结束后，判断「放完了」的是 UI 每 500ms 一次的
轮询。在它发现之前，USB 线程会继续按 microframe 节奏把空缓冲填成静音 ——
实测那段有 478ms，全部被记进 underrun。这跟解码能力毫无关系，纯粹是收尾慢。

**其二：重采样器的尾巴从没被取出来。** `Resampler::flush()` 声明了、实现了、
**但没有任何调用点**。swresample 有内部滤波器延迟线，喂完最后一块输入时那部分
还没变成输出，必须显式 flush 才会交还。

用 ffmpeg 的同款 `aresample`（同一套 swresample、同样 `filter_size=32`）验证：

```bash
ffmpeg -i in.flac -af "aresample=48000:filter_size=32:cutoff=0.97:dither_method=none" \
       -f s32le out.s32
# 输出 16340480 帧，正好 = 15012816 × 48000/44100
```

而设备实收有效帧数比它少 **4,842 帧（0.1 秒）**。

> **事后更正**：当时把这 0.1 秒整个归因于「没调 flush」，这是错的。
> 补上 flush 之后实测只回收了 **18 帧**（与 `filter_size=32` 的滤波器延迟吻合），
> 剩下 4,096 帧另有原因 —— 见下面「起播丢帧」。flush 确实该补（它是个真 bug），
> 但它不是那 0.1 秒的主因。

修复分三处：

1. `AudioEngine::decodeLoop()` 在解码到末尾时调用 `flushResampler()`，
   把尾巴写进环形缓冲**之后**才置 `finished_`（顺序要紧 —— 数据源的
   `finished()` 要求「解码结束**且**缓冲排空」，否则刚写进去的尾巴会被跳过）。
2. 补上 `PcmSource::finished()` 的实现（此前是个从未被使用的空接口）。
   `RingBufferSource::finished()` = 解码已结束 **且** 缓冲已排空。
3. `IsoPlayer` 据此主动收手：在 `onIsoComplete` 里判断，放完就置
   `stopRequested_` 且不再重提交 URB。

第 3 点必须做在回调里而不是主循环里：主循环 100ms 才醒一次，这期间仍会填进
上百个 URB 的静音。而回调里**只能置标志、不能调 `stop()`** —— 回调跑在 libusb
事件线程上，`stop()` 会 join 同一个线程，从回调里调用就是死锁。

现在残留的欠载最多一个 URB（192 字节 ≈ 1ms），且那确实是「最后一帧送完、
流自然结束」的边界填充。

### 已修：每次播放都丢掉开头 93ms

引擎计数加进来之后，实测放完一整首后是这样的：

```
解码器交出: 15008720 源帧
文件实际帧数: 15012816 源帧        ← 用 ffmpeg 解同一文件核对
差额:          4096 帧 = 93ms      ← 恰好一个 kDecodeChunkFrames
```

**恰好一块**，这个数字太工整，不像随机丢帧。追下去发现是起播预灌的锅：

`writeToRing()` 的循环条件里带着 `stopRequested_`，而这个标志经
`open() → close() → stopDecoding()` 之后会**残留为 true**（`stopDecoding`
无条件置位，`close` 不会复位它）。同时 `startDecoding()` 把它清零的语句
却写在预灌循环**之后**：

```cpp
    while (ring_.available() < targetBytes) {
        const int got = decoder_->readFrames(...);   // ← 读走 4096 帧
        ...
        if (!writeToRing(...)) break;                // ← written=0，返回 false，break
    }
    stopRequested_.store(false);                     // ← 太晚了
```

于是每次播放：第一块 4096 帧被解码器消费掉，却因为 `stopRequested_` 还是 true
而一个字都没写进缓冲，**凭空消失**。

后果有两个，都很难察觉：

- 每次播放都从第 93ms 开始，开头被静默切掉。歌曲以淡入开始时听不出来，
  开头是强瞬态时才能察觉
- **预灌从来没生效过**，起播时缓冲是空的。实测残留的 356 字节欠载就是这个 ——
  解码线程填得快，只欠了两个 URB

修法就是把 `stopRequested_.store(false)` 挪到预灌循环之前。

### 已修：主动取消的 URB 被算成传输失败

自动停止时会 `libusb_cancel_transfer` 掉在途的 URB，它们以
`LIBUSB_TRANSFER_CANCELLED` 收场，被计进了 `urbsFailed`：

```
URB 完成=340329  URB 失败=6   最近传输状态=3 (LIBUSB_TRANSFER_CANCELLED)
```

于是一首**正常播完**的歌，报告上看起来像传输出错了 6 次。这跟「收尾静音被记成
欠载」是同一类问题：诊断数字把正常行为报成了故障。

现在按 `stopRequested_` 区分 —— 只有停止流程才会取消传输，而它第一件事就是置
这个标志。主动取消单独计数，且只在非 0 时显示：

```
URB 完成=340329  URB 失败=0  包错误=0  停止时取消=6（正常，不算失败）
```

### 已修：界面上的「缓冲水位」其实是播放进度

`tvPlayStats` 里那行 `缓冲水位: N%` 是用 `posMs * 100 / fileDurationMs` 算的 ——
**那是播放进度，不是缓冲深度**。用户照着这个数报告「卡顿发生在水位 18%/35%/62%/88%」，
等于报的是"歌播到哪儿"，把排查方向整个带偏了。

现在分两个数显示，各归各位：

```
播放中 1:23 / 5:40                     ← 进度（tvStatus，时间形式）
传输: 重采样
缓冲: 187392 / 192000 字节（97%）   欠载累计: 356 字节   ⚠ 水位偏低
```

水位低于 25% 时会显式警示 —— 卡顿就发生在那一段。

### 诊断：欠载事件清单

只有「累计欠载字节数」是不够的：用户能听出"卡了几次"，而报告里只有一个总数，
两边根本没法核对。现在每次缓冲见底都记一条，含**位置**和**补静音时长**：

```
欠载事件: 3 次
  #1  第 61.4 秒   补静音 2304 字节 ≈ 12.0 ms
  #2  第 118.9 秒  补静音 1536 字节 ≈ 8.0 ms
  #3  第 210.2 秒  补静音 3456 字节 ≈ 18.0 ms
```

两个实现细节：

- **按时间窗合并**。缓冲见底时 USB 线程会一个 URB 接一个 URB 地补静音
  （每个 URB 8 个 microframe），每次都调一遍 `fill`。不合并的话，一次听感上的
  卡顿会被拆成几十条记录。相距 100ms 以内的欠载算同一次。
- **位置是绝对播放位置**。事件里的帧计数自上次 seek 起算（seek 会把
  `writtenFrames_` 清零），所以报告时要把 `seekBaseMs_` 加回去 ——
  否则 seek 之后报的"第 5 秒"其实是"seek 之后第 5 秒"。

上限 20 条，超出会明说"另有 N 条未记录"，不会假装只有 20 次。

### 诊断：引擎计数

为了定位上面那 0.1 秒到底丢在解码段还是重采样段，`nativeStopPlayback`
现在还会输出：

```
── 引擎计数 ──
解码器交出: N 源帧（... 秒）
写入缓冲:   M 输出帧（... 秒）
期望输出:   K 帧（解码帧数 × 48000/44100）
差额:       M-K 帧（... ms）  ← 不为 0 就说明重采样这一段少了或多吐了
```

`解码器交出` 与文件本身的帧数一致 → 解码段没问题；`差额` 接近 0 → 重采样段也没问题。
两个数一夹，问题只能出在别处，不用再猜。

**怎么读 `差额`**：几个帧的**正值**是正常的，那是 flush 回收回来的滤波器延迟尾巴
（`filter_size=32` 对应约 18 帧 = 0.4ms，听感上完全不存在）。
要警惕的是**负值**，或者绝对值到千帧量级。

**已修：预灌的帧没被计入 `decodedFrames_`。** 起播预灌会从解码器取走约 11 块
（45,056 源帧 = 1 秒），原来只写进环形缓冲、没计数，于是 `差额` 恒定多出 1 秒：

```
文件实际帧数 15012816 − 解码器交出 14967760 = 45056 = 正好 11 × 4096
45056 × 48000/44100 = 49041 = 报告里的差额（实测值，分毫不差）
```

顺带一提，那次的 `写入缓冲 = 16340480 = 正好等于 15012816 × 48000/44100`
—— 输出是**精确正确**的，一个样本没丢，只是记账缺了一段。
这个校验在修好之前其实是失效状态，别拿它下结论。

> 报告里那句「不为 0 就说明重采样这一段少了或多吐了」写得过于绝对，
> 下次改动时一并修掉措辞。

### 已修：高采样率下点播放会卡死

缓冲目标水位原本写死成「1 秒的数据」，没有对容量封顶。而 384kHz/24bit/2ch
的单秒数据是 2.3MB，比整个环形缓冲（2MiB）还大：

```
预灌循环：while (ring_.available() < targetBytes)   ← 永远成立
```

而那一刻 USB 线程还没启动、没人在消费，`writeToRing` 写不进去并空转 ——
点下播放后整个界面卡死，且没有任何日志。

受影响的是 352.8k/24bit、352.8k/32bit、384k/24bit、384k/32bit 四组
（正是 DSD 与最高解析度所在的档位）。现在目标水位封顶到容量的一半。

`tools/verify_buffer_math.py` 会遍历全部速率/位深组合，把「单秒数据超过缓冲容量」
的组合全列出来，可随时重跑。

### 任务 12 的软件层面验证（已完成）

两个示例文件（同一首曲子的 FLAC 与 ALAC 版本，均 44.1kHz/16bit/5:40）:

```bash
ffmpeg -i "願い EP/01. 願い〜あの頃のキミへ〜.m4a"  -map 0:a:0 -f s32le alac.s32
ffmpeg -i "願い E.P.../1.1.願い〜あの頃のキミへ〜.flac" -map 0:a:0 -f s32le flac.s32
md5sum alac.s32 flac.s32
```

结果：两者均 120,102,528 字节，MD5 同为 `b931b2d07c3968ae1114d5068d860aba`
—— **解码结果逐比特完全相同**。这验证了解码通路本身没有引入任何偏差，
剩下的差异只可能来自重采样与 USB 传输。

按 `rate_policy.h`，这两个 44.1kHz 文件会被重采样到 48kHz 输出
（本设备不支持 44.1k 家族），因此它们**不是** bit-perfect 播放；
换一台原生支持 44.1k 的小尾巴即可直通。

## 端到端 bit-perfect 验证（输出字节转储）

上面那个验证只证明**解码器**没有偏差。它说明不了整条通路 ——
重采样、位深转换、字节序搞反，全都能在"欠载 0、URB 零失败、缺口 0"
的前提下悄悄发生。**所有那些指标都只说明"没出错"，说明不了"送出去的
字节和文件里的一模一样"。**

唯一能证伪的办法，是把**真正交给 USB 的字节**留下来，和 PC 上的参考逐字节比。

### 怎么做的

界面上勾选**「输出字节转储」**。原生层在 `IsoPlayer::prepareTransfer`
里把 `PcmSource::fill()` 返回的**有效字节**（即 `valid`，不含欠载/暂停补的
静音）原样累积到一个内存缓冲，停止播放时写到：

```
/sdcard/Android/data/com.hifiprobe/files/hifiprobe_dump.raw
```

两个设计上的取舍：

- **只进内存，不在 USB 线程上做文件 I/O。** 那个线程是实时的 ——
  一次阻塞写盘就正好复现我们花大力气修掉的卡顿（提交被挂起 → 队列抽干）。
  上限 32MB（48k/24bit 下约 111 秒），超出后停止累积并在报告里注明。
- **必须在 `player.stop()` 之后落盘。** `stop()` 会 join libusb 事件线程，
  那之后缓冲才不再有人写；播放中写就是数据竞争。
  同理，缓冲的清空放在 `start()` 里 —— 那里刚判过 `running_`，
  保证没有 URB 在跑。**不清的后果很隐蔽：第二遍会追加在第一遍后面，比对直接失败。**

### 怎么用

```bash
# 1. 手机上：勾选「输出字节转储」→ 选文件 → 播放 → 停止
# 2. 拉回来（MSYS_NO_PATHCONV 必须加，否则 Git Bash 会把 /sdcard 当 Windows 路径）
MSYS_NO_PATHCONV=1 adb pull \
    /sdcard/Android/data/com.hifiprobe/files/hifiprobe_dump.raw \
    C:/Users/123/Desktop/hifiprobe_dump.raw

# 3. 一条命令出结论（生成参考 + 逐字节比对）
cd C:/Users/123/Desktop/hifiprobe
./tools/bitperfect_check.sh "<源文件.flac>" C:/Users/123/Desktop/hifiprobe_dump.raw
```

`compare_dump.py` 不会只说"不一样"，它会先排除**可解释的差异**
（整体平移 / 字节序反了 / 位深不一致），剩下才谈真问题：

| 结果 | 含义 |
|---|---|
| 逐字节完全相同 | bit-perfect 得证 |
| dump 是参考的前缀 | 送出的都对，只是没播完（截断或手动停）——**不算缺陷** |
| 参考是 dump 的前缀 | 内容全对，多出来的是收尾静音 ——**不算缺陷** |
| 其它 | 报出首个差异字节、落在第几帧/哪个声道，再给诊断 |

### 验证它的前提

不满足这几条，比对**必然**失败 —— 但那是预期行为，不是缺陷：

- **播放时没有重采样。** 源文件采样率必须落在设备的"正常"档
  （48000 / 96000 / 192000 / 384000）。44.1k 家族会被重采样，输出的
  字节本来就该和文件不同。
- **不要 seek。** 开了「seek 清队」时被取消的 URB 会乱序重填，
  转储就不再是线性的了。暂停是安全的（暂停期间 `fill()` 返回 0 有效字节，
  什么都不追加）。
- **没开任何音量 / DSP 处理。**

### 它证明了什么、没证明什么

- **证明了**：从解码器到 USB 缓冲这一段，字节一个没变。
- **没证明**：这些字节在物理链路上没有出错。但 iso 端点不重传，
  且 `URB 失败 / 包错误` 两个计数器恒为 0 —— 两者合起来才构成完整结论。

### 实测结果（2026-09-22，p18）

用 **176.4 kHz / 24bit** 的真实音乐（DSD256 源转出的 20 秒片段）跑了一遍：

```
转储文件  : dump_p18.raw            6,120,834 字节
参考 PCM  : spring_mid_176k.ref.s24  21,168,000 字节
帧格式    : 2ch × 3B = 6 B/帧
✓ 转储是参考的**前缀** —— 送出去的每一个字节都对
   1,020,139 帧，一个字节都没变
```

**bit-perfect 得证，而且是在 176.4 kHz 上** —— 一个旧表里被列为"失真"的速率。
传送链路、环形缓冲、线格式转换、24bit 打包，整条路上一个字节都没变。

### 踩过的坑：转储缓冲的**内存重分配**会把实时线程卡死

第一版把转储写成 `dumpBuf_.insert(...)`，**没预留容量**。结果 vector 按几何级数
增长，每到 4/8/16/32MB 就要在**原地复制整个缓冲** —— 而这段代码跑在
**USB 提交线程**上。四段测试全部中招，提交间隔的指纹是：

```
第 4.108 秒   卡 149.953 ms
第 8.293 秒   卡 225.742 ms
第 16.78 秒   卡 442.095 ms
```

**发生时刻精确翻倍（4.1→8.3→16.6→33.2→66.4 秒），卡顿时长随缓冲大小同步增长** ——
这是重分配的特征，和调度器抖动完全不是一个形状。队列被打穿，
听感是明显卡顿，一度让人以为是 176.4k 速率本身的问题。

修法是一行：`start()` 里 `reserve(kDumpLimitBytes)`，让 append 永不扩容，
只剩一次几 KB 的 memcpy（微秒级）。

**教训**：README 里写了「绝不在 USB 提交线程上做文件 I/O」，
却没料到**内存重分配一样致命** —— 它同样是一次不可控的长阻塞。
在实时线程上，「分配」和「I/O」是同一类危险，不是两类。

**顺带一个方法论收获**：这次能一眼定位，靠的是**「提交间隔」带时刻**。
只有「最大 442ms」是不够的 —— 加上「发生在第几秒」，翻倍的规律才浮出来。
这正是本项目一贯的做法：把看不见的状态变成报告里的一行字，**并且带上时刻**。

## 界面设计规范

一套语义化的设计系统，不是"随手调的颜色"。核心约定只有三条，但都很容易被无意破坏。

### 一、颜色一律用语义名，禁止字面量

```
res/values/colors.xml        浅色（默认）
res/values-night/colors.xml  深色（键名严格一一对应）
```

按**用途**命名而不是按颜色：`text_secondary` 而不是 `gray_600`。这样换配色只改一个文件，
不必去每个布局里找"哪个灰该换成哪个灰"。

层级只有五档，够用且不会失控：

| 名称 | 用途 |
|---|---|
| `bg` / `surface` / `surface_alt` / `border` | 底、卡片、次级面、描边 |
| `text_primary` / `text_secondary` / `text_tertiary` | 文字三级 |
| `brand` / `on_brand` | 主色及其上的文字 |
| `ok` / `warn` / `error` | 语义三色，**不要混用** |

`ok` 专指"直通 / bit-perfect"—— 这是本播放器最重要的一个状态，绿色不能被别处借走。

**Kotlin 代码里也不许出现颜色字面量**，一律走 `Ui.c(ctx, R.color.xxx)`。
写死了的话，浅色主题下就会冒出一堆看不清的浅色文字。

### 二、所有 Material3 颜色角色都要显式映射

`themes.xml` 里把语义色灌进 M3 的颜色槽。**漏一个，对应的控件就会回落到框架默认的紫色。**

已经踩过两次：

- 漏了 `colorSecondaryContainer` → 传输按钮变成淡紫（TonalButton 用它）
- `IconButton.Filled` 自带的 `backgroundTint` 会**连我们设的 `android:background` 一起染色**
  → 播放键变成洋红

凡是"某个控件颜色不对"，先回 `themes.xml` 看是哪个槽没接。

### 三、图标用矢量，不用字符

`⏮ ⏯ ⏭` 这些码位**默认走 emoji 字体**，会被渲染成彩色方块，
和界面其余部分的单色风格完全不搭（实拍截图里那个橙色暂停键就是）。
统一用 `res/drawable/ic_*.xml`。

### 排版与间距

字号四级：`Text.Screen`(21) / `Text.Section`(13) / `Text.Title`(15) / `Text.Meta`(11)。
间距只两档：页面 16dp、卡片间 12dp。

**统一风格最难的部分不是配色，是这类没人管的碎数值。** 之前同一个「副标题」
在三个界面里有三种字号、四种灰，就是因为它们是散落在各处的字面量。

### Android 15 的 edge-to-edge

targetSdk 35 起系统**强制 edge-to-edge**，内容会顶到状态栏底下 ——
实拍时标题直接和时钟叠在一起。每个界面的根布局都要调 `Ui.applySystemBars()`。

用 insets 监听而不是 `fitsSystemWindows="true"`：后者在某些机型 + 手势导航的
组合下算不准底部，而我们的底部正好有迷你播放条，压到导航条上会按不着。

### 主题切换

`App`（Application 子类）在建任何界面之前调 `AppCompatDelegate.setDefaultNightMode()`。
放在 Application 而不是各 Activity 的 `onCreate`：后者每进一个界面都会触发
一次配置变更 → Activity 重建 → 闪一下。

## 安装

交付包放在工程根目录，文件名带版本号：

```bash
adb install -r HiFiProbe-v0.1-p1-debug.apk
```

或直接把 APK 传到手机点击安装（需允许「安装未知来源应用」）。

- 最低 Android 8.0（API 26）
- **仅 arm64-v8a**。FFmpeg 只为该 ABI 交叉编译过，`abiFilters` 里也据此写死；
  要支持 armeabi-v7a 得先用 NDK 跑一次 FFmpeg configure + make，
  再把产物补进 `jniLibs/armeabi-v7a/`。目标机型是 arm64，暂无此需要。
  （P0 时代的包曾同时带 v7a，那是 FFmpeg 还没接入时的遗留。）
- **不需要存储权限**——USB 权限走系统弹窗（不属于 Android 危险权限体系），
  文件走 SAF。
- 唯一会索取的运行时权限是 **通知**（API 33+），用于播放期间的前台服务通知。
  **拒绝它不影响任何功能**：前台服务照常运行、防冻结照常生效，只是那条
  常驻通知不显示。

> 装之前先确认版本。打开 App 的第一行日志会显示
> `HiFiProbe <版本> (versionCode N)   安装于 <时间>`，导出的报告头部也有同样一行。
> 同一版本号反复编译时，**安装时间**是唯一能区分构建的字段。
> 交付新包时版本号必须往上走一位，避免根目录堆积同名不同行为的 APK。

## 测试流程

插上小尾巴，按顺序点这些按钮（①②③ 是 P0 诊断，⑦ 是 P1 播放）：

| 步骤 | 按钮 | 验证什么 |
|---|---|---|
| ① | 解析 UAC 描述符 | 纯 Java 读原始描述符，输出 DAC 完整能力表 |
| ② | 原生探针 | **关键步骤**：libusb 能否接管 Java 传来的 fd |
| ③ | 抢占接口 | 能否把接口从系统音频栈手里抢过来 |
| ④ | BIT_PERFECT 检测 | 低成本备选路线是否可行 |
| ⑤ | 开始出声测试 | 真正提交 isochronous 传输，耳机里应响起 1kHz 蜂鸣 |
| ⑦ | 选择音频文件并播放 | **P1 主功能**：解码真实文件并经同一条 iso 通路播出 |

⑦ 与 ⑤ 走的是同一批 USB 接口，所以两者互斥 —— 点其中一个会自动收掉另一个。

最后点「导出完整报告到文件」，报告会写到：

```
/sdcard/Android/data/com.hifiprobe/files/hifiprobe_<时间戳>.txt
```

用 `adb pull` 取回：

```bash
adb pull /sdcard/Android/data/com.hifiprobe/files/
```

## 怎么判断结果

**P0 通过** = ② 显示 `nativeOpen 成功` **且** ⑤ 耳机里听到 1kHz 蜂鸣、小尾巴采样率指示灯跳到你设定的频率。

### 如果 ② 失败

这是最坏情况，意味着该 ROM 下自研 UAC 驱动路线走不通。报告里会带 libusb 的具体错误码：

| 错误 | 含义 |
|---|---|
| `LIBUSB_ERROR_ACCESS` | SELinux 拦截，或 fd 无效 |
| `LIBUSB_ERROR_NOT_SUPPORTED` | `wrap_sys_device` 在该 ROM 被禁 |
| `LIBUSB_ERROR_IO` | `USBDEVFS_CONNECTINFO` ioctl 被拒 |

### 如果 ③ 失败但 ② 成功

问题不大——反而说明音频接口本来就空闲，用不着抢。

### ④ 的预期结论

`setPreferredMixerAttributes` 需要 `MODIFY_AUDIO_ROUTING`，这是 signature|privileged 级权限，
普通三方应用拿不到。所以这一步**大概率会全部失败**，这是预期内的，
它排除掉的是一条本来就不可行的捷径。

## 关于 ⑤ 出声测试的一些细节

- 播放的是 **1kHz 正弦波**，不是静音——静音测不出问题
- 音源用相位累加器实时生成，**不做 ring buffer**，从结构上排除 underrun 干扰
- 44100Hz 这类不能被 8000 整除的采样率，包长按 Bresenham 算法在 44/45 字节间交替分配，
  保证长期零漂移
- 自动选择**子帧字节数与位深匹配**的无歧义格式（如 24bit/3字节），
  避开 24bit 装 4 字节容器时的对齐歧义
- 若设备是异步 DAC，会额外读取 feedback 端点并把 Q16.16 值换算成实际采样率

播放中状态栏每秒刷新 URB 完成数、累计字节、单包字节 min/max、feedback 实测速率。
**单包字节 min/max 应该稳定在两个相邻值上**（如 44/45），如果波动很大说明调度有问题。

## 两条重要的生命周期约束

违反会直接崩，改代码时务必留意：

1. **`UsbDeviceConnection.close()` 必须在 `nativeClose()` 之后调用。**
   libusb 包裹的就是这个 fd，提前关闭会导致原生层后续 ioctl 全部 `EBADF`。

2. **原生层工作期间不要在 Java 侧 `claimInterface()`。**
   两边操作的是同一个 fd，同时 claim 会互相打架。claim 统一由原生层做
   （见 `MainActivity.runClaimTest()` —— 它测完会立刻 release）。

## 把音乐传进去：三种客户端，一套接口

手机 App 起一个 HTTP 服务（`WirelessServer`，默认 8765），**三种客户端走同一个
`POST /upload`**，App 那边零分支：

| 客户端 | 入口 | 适合 |
|---|---|---|
| **网页** | 浏览器打开 `http://<手机IP>:8765` | 拖几个文件、临时看看库里有什么 |
| **图形界面** | 双击 `上传到手机.pyw` | 平时用这个 —— 能先体检、能选目标目录 |
| **命令行** | `python tools/hifiprobe-upload.py --host <IP> <文件夹>` | 批量、脚本、几万个文件 |

### 为什么要有自己读文件的客户端

**260 字符那个上限在 Chrome，不在 Windows。**（2026-09-24 实测，见下）

网页上传时**打开本地文件的是 Chrome**，它自己设的上限我们够不着；而且它读不到的文件
会让**整批选择一起失败**，还不说是哪个。自己读文件就没这些事：

- 上传**之前**逐个试读，把读不到的连完整路径和真实原因一起列出来
- 不经过浏览器，不受它任何路径上限影响
- 几万个文件流式发，不吃内存

### 图形界面（`tools/hifiprobe-upload-gui.pyw`）

纯标准库 Tkinter，**不用 pip、不用打包**。`.pyw` 关联 `pythonw.exe`，
双击**没有控制台黑框**（起不来的话用同目录的 `.bat`，那个带控制台能看报错）。

功能对齐网页那套 JS，逐条：

| 网页 JS | GUI |
|---|---|
| `select[name=dir]` 选目标目录 | 折叠目录树 + 单选钮（+ 过滤框） |
| `input[name=newdir]` 新建目录 | 三选一：根目录 / 已有目录 / 新建目录 |
| `conflict()` 重名预检 | 同规则，冲突则**一个字节都不发** |
| `pickDir` / `pickFiles` | 「添加文件夹…」/「添加文件…」，也支持拖多个进 `argv` |
| `pickErrors` | 逐个试读 + **放不了的格式也报出来** |

* **目录树默认全折叠** —— 真实库 202 个目录、但顶层只有 8 个，折叠后一屏放得下。
* 窗口默认 1600×1280，**记住上次的大小和位置**。
* 行高按字体实际行高算（`linespace + 12`），换机器/缩放都不会错位。
