# 一、已确认的 bug

## ✅① 歌单页多选：勾选圈和行**错开一行**　【用户报的】

| | |
|---|---|
| 报的人 | 用户，2026-09-25 |
| 状态 | ✅ **已修**（release vc101） |
| 修在 | `app/src/main/java/com/hifiprobe/PlaylistsActivity.kt` 两处调用点 |

### 用户原话（按时间顺序，一字不差）

1. 「多选后选项没有对齐按钮是错开的」
2. 「勾选后圈变绿色但是绿色没有对齐」
3. 「我的意思是现在歌单里有两个，我选择第一项圈没有变绿，选两项只要绿第一项，
   **是不是新建歌单占位了**」

★ **第 3 句点破了根因 —— 用户自己猜对了。**
前两轮我把「没对齐」理解成了"drawable 尺寸 / tint 把勾染没了"，查错了地方。
**"没对齐"指的是"圈和它该在的那一行对不上"。**

### 根因

列表第 0 项固定是「新建歌单」，所以 **adapter position 和「`playlists` 数组下标」差 1**：

```kotlin
override fun getItemCount() = playlists.size + 1     // ★ 多了一项
val p = playlists[position - 1]                      // bind 里减 1 —— 对的
...
if (sel.active) toggleOne(p.id, position - 1)        // ✗ 调用点又减了 1
private fun toggleOne(id: String, position: Int) {
    listAdapter.notifyItemChanged(position)          // ✗ 却当 adapter position 用
}
```

结果 `notifyItemChanged` **永远刷新上一行**：

| 用户点 | adapter position | 实际刷新 | 现象 |
|---|---|---|---|
| 第 1 项 陈奕迅 | 1 | position 0 =「新建歌单」 | 陈奕迅的圈**不变** |
| 第 2 项 milet | 2 | position 1 = 陈奕迅 | **陈奕迅变绿，milet 不变** |

★ `sel.toggle(p.id)` 本身是**对的** —— 选中数量、底部按钮都正常，
**只是圈画在了错的那一行**。所以这不是"选中失效"，是"显示错位"。

### 修法

两个调用点传 **adapter position**（各删一个 `- 1`），`toggleOne` / `bind` 不动：

```kotlin
if (sel.active) toggleOne(p.id, position) else openPlaylist(p)
if (sel.active) { toggleOne(p.id, position); true } else false
```

### 影响面

**只有歌单页**。其它页 `getItemCount()` 都不含额外行：

| 页面 | `getItemCount()` | 有 header 吗 |
|---|---|---|
| `AlbumsActivity` | `albums.size` | 无 |
| `LibraryActivity` | `rows.size` | 无 |
| `QueueActivity` | `items.size` | 无 |
| `TrackListActivity` | `rows.size` | 无 |
| **`PlaylistsActivity`** | **`playlists.size + 1`** | **有（第 0 项 =「新建歌单」）** |

### 真机验证（vc101）

| 点之前 | 点第 1 项之后 |
|---|---|
| 两项的圈环上都是 `#5A6B7C` 灰、圆心白（空心） | **第 1 项：环上 + 圆心都是 `#12796B` 绿（实心）** ✅<br>**第 2 项：仍是空心灰** ✅ |

## ✅④ 勾选圈三态被 `imageTintList` 压平

| | |
|---|---|
| 发现 | 2026-09-25，查 ① 时撞上的**另一个**真实缺陷（用户没报这个） |
| 状态 | ✅ **已修**（release vc101） |
| 修在 | `ic_check_on.xml`、`ic_check_partial.xml`、`ic_check_off.xml` |

### 根因

`ic_check_on` 原本是**实心圆 + 白勾**两个 path。但渲染代码是"换 drawable + 换 tint"：

```kotlin
vh.check.setImageResource(if (on) R.drawable.ic_check_on else R.drawable.ic_check_off)
vh.check.imageTintList = ColorStateList.valueOf(
    Ui.c(act, if (on) R.color.brand else R.color.text_secondary))
```

`imageTintList` 默认按 **`SRC_IN`** 混合：把 drawable 里**所有不透明像素统一换成 tint 色**。
两个 path 原本都是白的 → **圆和对勾变成同一个绿色** → **对勾彻底看不见**。

★ 半选的**白横线**同理消失 → **半选和全选长得一模一样**，三态退化成两态。
而 `ic_check_partial.xml` 的注释明说三态是必需的。

★★ 5 个页面都是这个写法：`LibraryActivity:848`（歌曲行）/ `:807-814`（文件夹三态）/
`PlaylistsActivity:358` / `AlbumsActivity:288` / `QueueActivity:395` / `TrackListActivity:725`。

### 修法

**把对勾/横线改成从实心圆里"镂空"** —— 一条 path 配 `fillType="evenOdd"`，
勾（横线）围出的区域被挖掉，透出背景色。**7 处 Kotlin 渲染代码一行没动。**

★★ 这个 App 背景是白的，所以镂空出来**正好就是原来的"白勾"** ——
设计意图一分不差地保住，而且单一 tint 色再也吃不掉它。

★ 勾的轮廓是把原折线按 strokeWidth 1.9 手工外扩成多边形（内角走 miter）；
横线是把 `M7.5,12 L16.5,12`（2.2、圆头）外扩成矩形。
★ `ic_check_off` 半径 **8 → 8.2**，让描边外缘（8.2+0.8=9）和实心圆外缘对齐。

### 真机验证（vc101，像素采样）

| 状态 | 采样结果 |
|---|---|
| 未选 | 环上 `#5A6B7C` 灰、圆心白 → **空心灰圈** ✅ |
| 全选 | 环上 + 圆心全 `#12796B` 绿；**勾的三个采样点全白** → **绿实心圆 + 镂空白勾** ✅ |
| 半选 | **横线三点全白**、线上下方全绿 → **绿实心圆 + 镂空白横线** ✅ |

**半选和全选现在分得开了** —— 三态恢复。

## ⑧ 播放中打开「诊断页」→ 断连 + 之后播放不了

| | |
|---|---|
| 报的人 | 用户，2026-09-26 |
| 原话 | 「如果在播放中打开设置的诊断页有bug」→ 追问后补充：<br>**「打开后，是不是和我们的原本的冲突会导致首页显示未连接解码器 + 重连后按播放无法播放」** |
| 状态 | ⛔ **用户定：不修**（2026-09-26） |

★ **用户自己猜对了方向**（"是不是和我们的原本的冲突"）。
★ 工程注释里本来就写着这件事：
  「现在有两个界面都可能开设备（媒体库页自动打开、诊断页手动打开），各持一份必然出事」。

### 根因（`MainActivity.kt`，两个机制叠在一起）

**① `connection` 被无条件顶掉**（这是「未连接解码器」的来源）

```kotlin
private var connection: UsbDeviceConnection?
    get() = PlayerSession.connection
    set(value) { PlayerSession.connection = value }     // ← 直接写进全局

private fun openDevice(device: UsbDevice) {
    val conn = usbManager.openDevice(device)
    connection = conn                                    // ★★ 无条件覆盖
    ...
    if (nativeHandle == 0L) { … }                        // handle 非 0 才跳过开引擎
```

播放中进诊断页 → `connection` 被换成诊断页新开的那个 →
**旧的那个 `UsbDeviceConnection` 失去引用 → GC 时关掉底层 fd** →
正在播的那条 USB 断了 → **首页显示「未连接解码器」** ✓

★ 注意 `if (nativeHandle == 0L)` 只挡住了"重复开引擎"，
  **没挡住 `connection` 的覆盖** —— 这就是漏掉的那一环。

**② 诊断页会主动「停止播放并释放接口」**（这是「播放被打断」的来源）

`MainActivity` 里有几处会打印 `「检测到上一次仍在播放，先自动停止并释放接口。」`
并真的去停 —— 播放中进诊断页点相关按钮就会把正在播的会话停掉。

**③ 两边状态对不上**（这是「重连后按播放无法播放」的来源）

诊断页的操作把 `handle` / `connection` 换掉或归零了，
但 **`PlayerSession` 里那套播放状态（nowPlaying / 队列 / 引擎上下文）没跟着清** ——
于是两边描述的不是同一个会话，重连之后按播放就对不上了。

### 为什么没实测

`uiautomator dump` 在这次会话里**对这个 app 的页面普遍失败**
（`ERROR: null root node returned by UiTestAutomationBridge`，
首页/音乐库页偶尔成功，设置页和播放页一直失败），
而 `MainActivity` 和 `LibraryActivity` 一样**没导出**，`am start` 进不去。
→ **这部分靠用户确认**。

### 怎么办 —— **不修**（用户 2026-09-26 定）

用户原话：**「不需要了，我一般不会使用到这个诊断页，而且正式版也不会有这个问题」**

★ 两条理由都成立：
  1. 诊断页是**开发者工具**，日常用不到（内部版也是出问题才翻）
  2. **正式版会把诊断和调试屏蔽掉**（见 FACT 待办），这个 bug 在那条线上不存在

★ **所以不要为它花时间。** 留这条记录的价值只有两个：
  · 万一以后又有人往诊断页加"顺手开设备"的代码，这里写清了**为什么不能那么写**
  · 它暴露的那个设计脆弱点是真的 —— **设备状态（handle / connection）是全局单份的**，
    谁新开一份都会顶掉正在用的那个。**将来加任何"暂时用一下设备"的功能，
    必须先想清楚会不会顶掉播放会话。**

★ 如果哪天决定内部版也修，候选（按推荐顺序）：
  1. 诊断页开设备前先判断"正在播放"，是的话**拒绝并提示**
  2. 复用 `PlayerSession.connection`，不另开
  3. 播放中直接禁用诊断页入口

## ⑦ USB 瞬时重新枚举 → app 卡死在「PLAYING / 位置恒 0」

| | |
|---|---|
| 报的人 | 用户，2026-09-26 |
| 原话 | 「你看一下现在什么情况，进度条拖到原点以后不能播放了」<br>→ 追问后：「我好像复现不了了，难道问题是我解码器的usb松动了吗」 |
| 状态 | ⏳ **成因未确认，用户明确说「不要贸然更改」** |

### 现象（实测钉死）

`/debug/state` 连采三次，**`state=PLAYING` 但 `positionMs` 恒为 0**，纹丝不动：

```
t0  state=PLAYING  positionMs=0  queue=8  Piano Concerto No. 1 …
t1  state=PLAYING  positionMs=0  queue=8  Piano Concerto No. 1 …
t2  state=PLAYING  positionMs=0  queue=8  Piano Concerto No. 1 …
```

界面**看不出任何异常** —— 既不报错也不暂停，就是不出声。

★ 用户以为是"拖进度条到 0"引起的，**这个因果不成立**（见下）。

### 现场还原（13:04:11.002 那一毫秒）

| 层 | 日志 | 含义 |
|---|---|---|
| **USB HAL** | `auto suspend usb interfaces /sys/devices/.../a600000.dwc3/…`<br>`fopen failed in writeFile …/dwc3/…` | HAL 去动 dwc3 控制器，**写 sysfs 失败** |
| **内核 ALSA** | `UsbAlsaManager: Adding ALSA device card=1`<br>`alsaFileAdded(pcmC1D0p)` | **声卡被重新创建** —— 设备被重新探测 |
| **app（libusb）** | `LIBUSB_TRANSFER_NO_DEVICE` ×31<br>`设备已断开（NO_DEVICE），停止播放` | **旧 fd 作废**，播放停止 |
| **USB 拓扑层** | `UsbHostManager` **13:04 一条都没有** | 它认为设备**从没消失**（最后一次动作还是 12:20:58 的插入） |

**机制**：USB 链路瞬时抖了一下 → dwc3 控制器复位、设备重新枚举（**地址没变**，
所以拓扑层无感，不发 `USB_DEVICE_DETACHED`/`ATTACHED` 广播）→ ALSA 声卡重建 →
**app 手里的 fd 作废** → `NO_DEVICE` → app 卡死。

★ `/dev/bus/usb/002/002` 的节点时间戳是 **13:04**（原来是 12:20）—— 节点确实被重建过。
★ **设备其实还活着**：ALSA card 重建了、`dumpsys audio` 里 `usb_headset` 还在
  → **重新 open 一次就能恢复，根本不用拔插**。

### ★★ 成因未确认（**这就是不能动代码的原因**）

两个可能，**从日志区分不了**：

**可能 A：USB 物理接触不良**
- 判据：**同样那两句 HAL 日志，13:02:27 起播那一刻也出现过一次，那次什么事都没有** ✗
- 同样的软件动作，一次没事一次掉 → 差异在物理侧
- 旁证：工程里早就记着这颗 DAC 的怪癖（`native_bridge.cpp:2110`）——
  「所有软件层都是好的……可小尾巴就是不出声，**只有物理拔插一次能恢复**。
  残留状态在那颗 DAC 内部」

**可能 B：HAL 的 autosuspend 副作用**
- 判据：HAL 在 `auto suspend usb interfaces` 时 **`fopen failed in writeFile`**（写 sysfs 失败）
- 这个失败如果导致控制器状态机走偏，就可能是软件诱因

★ **两者都解释得通现有日志**，所以**现在改代码就是赌**。
★ 用户说的"复现不了了"也符合：它取决于那一下的物理接触，不取决于操作。

### 待办：怎么把成因定死

1. **复现时抓现场** —— 出问题时立刻抓 `/debug/state` + `logcat`，
   看有没有 `auto suspend` / `alsaFileAdded` 同时出现
2. **（可选）先只加观测，不改行为** —— 让原生层把 `NO_DEVICE` 上报、
   在诊断报告里记一行带时刻的字（**只记录，不触发任何重连/暂停**）
3. 观察一段时间：如果 `NO_DEVICE` 只在有 `auto suspend` 时出现 → 偏向可能 B；
   如果伴随物理扰动（插拔耳机线、碰到接口）→ 偏向可能 A

### 候选修法（**成因未定之前不动手**，只记在这）

1. **原生 `NO_DEVICE` → 上报 Kotlin** —— 
   它是这次**唯一**察觉到异常的一层，现在是它咽下去了
2. **`DeviceGate` 收到后先试一次 `ensureOpen` 自愈** ——
   设备还在的话用户几乎无感；真拔了才走 `onDetached()`（暂停 + 提示「设备已断开」）
3. **看门狗**：`PLAYING` 但位置连续 N 秒不推进 → 记一行字 + 触发上面那条路

★ 第 1 条是根，2、3 都是它挂出来的。
★ **注意**：修法 2 的"自愈"语义和用户 2026-09-26 定的
「拔掉 → 暂停、插回不自动继续」**不冲突** ——
自愈针对"设备其实还在（像这次）"，暂停针对"真的拔了"。
