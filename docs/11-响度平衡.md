## 一、要解决什么

同一个播放列表里，一首 1985 年的古典和一首 2020 年的流行，响度能差 **15~20 dB**。
听一张专辑还好，听歌单或随机播放就得不停摸音量键。

响度平衡就是：**让每一首听起来差不多响**，而不是看起来差不多峰。

---

## 二、先分清两件事，别混

| | 静态归一化 | 实时响度控制 |
|---|---|---|
| 别名 | ReplayGain / Sound Check / Spotify Normalize | AGC / loudness levelling |
| 做法 | 事先测出每首的响度，播放时乘一个**固定**增益 | 连续骑在增益上，追一个目标响度 |
| 动态 | 完全不动 | 被压扁 |
| 谁在用 | 消费级播放器、流媒体 | 广播台、电视台 |
| 本项目的取舍 | ✅ **要的就是这个** | ❌ 和"bit-perfect 直通"的气质正相反 |

★ **BS.1770 / EBU R128 是"测量"标准，不是"实时处理"标准。**
拿它做左边那列是对的；右边那列属于另一套东西（而且本项目的用户群体不会想要）。

## 三、标准里到底规定了什么

### 3.1 K 加权（BS.1770-4 §2）

两级滤波，串联：

1. **高频搁架**：约 1.5 kHz 以上抬 +4 dB —— 模拟人耳对中高频的敏感度
2. **高通**：约 38 Hz 二阶 —— 滤掉人耳几乎听不到、但会虚报响度的低频

★ 标准正文给的是 **48 kHz 的系数**。其他采样率要么按附录的模拟原型重算，
要么把测量统一重采样到 48 kHz。
**建议重算系数、按源采样率测** —— 测量不该反过来动源数据，而且省一次重采样。

### 3.2 分块与门限（BS.1770-4 §2.4）

- **400 ms 一块，75% 重叠**（即每 100 ms 滑一步）
- 每块算各声道的均方，按声道加权求和：`L=R=C=1.0`，`Ls=Rs=1.41`
- **两级门限**：
  1. **绝对门限** −70 LUFS —— 丢掉整块静音/极轻的段落
  2. **相对门限** = 过了绝对门限的均值 −10 LU —— 丢掉"前奏的钢琴独奏"这种
     拉低平均值的段落，否则一首歌会被开头 30 秒带偏

### 3.3 集成响度

```
L_KG = −0.691 + 10·log10( Σ_i G_i · z_i )
```

`z_i` 是过了两级门限的块的加权均方。单位 LUFS。

### 3.4 响度范围 LRA（EBU Tech 3342）

过了门限的块响度分布的 **10% ~ 95% 分位差**。用来看"这首歌动态大不大"。
不是必需的，但顺手就有。

### 3.5 真峰值（EBU Tech 3341）—— **不在 BS.1770 里**

**4 倍过采样**后取绝对值的最大，单位 dBTP。

★★ **这一项不是可选的**，理由见第八节。

### 3.6 目标值

| 场景 | 目标 |
|---|---|
| EBU R128 广播 | −23 LUFS |
| Spotify / YouTube | −14 LUFS |
| Apple Music | −16 LUFS |
| ReplayGain 2.0 | −18 LUFS |

真峰值上限：EBU R128 建议 **−1 dBTP**。

### 3.7 落到名字上：这就是 ReplayGain 2.0

★★ **说清楚我们到底在做哪一套，免得以后有人问"我们用的是哪种响度平衡"。**

| 方案 | 响度模型 | 我们 |
|---|---|---|
| **峰值归一化** | 看最大样本值 | ❌ BS.1770 就是为了取代它才有的 |
| **RMS 归一化** | 均方根 | ❌ 不考虑人耳加权 |
| **ReplayGain 1.0** | 83 dB 等响滤波 + RMS | ❌ 模型比 BS.1770 差一档 |
| **ReplayGain 2.0** | **ITU-R BS.1770** | ✅ **就是这个** |
| **EBU R128** | 同一套测量 | ✅ 同一套（R128 是它的广播侧应用） |
| **动态响度控制 / AGC** | 实时骑增益 | ❌ 压动态，见第二节 |

所以准确的表述是：

> **测量走 ITU-R BS.1770-4（集成响度）+ EBU Tech 3341（真峰值），
> 应用走 ReplayGain 2.0 式的静态增益。**

★ EBU R128 那个 **−23 LUFS 是广播目标**（给电视播出用的），
音乐场景一般不用它 —— 见 3.6 那张表。

## 四、接进现有通路：位置是现成的

原生层已经有逐样本的增益级，位置和交叉馈送**完全一样**：

```
解码 → [srcBuf] → 重采样(可选) → crossfeed → applyGain → convertS32ToWire → 环形缓冲 → USB
        ↑ 测量在这里 tap 源 PCM              ↑ 响度增益**乘进这一个系数里**
```

- `audio_engine.cpp:409-415`（起播预灌）和 `:544-550`（decodeLoop）**两处都要改** ——
  这个坑交叉馈送已经踩过一次，注释里写着"只改 decodeLoop 的话每首歌开头那一秒没效果"。
- 增益是 `std::atomic<float>`，解码线程每 `kDecodeChunkFrames = 4096` 帧重读一次
  （44.1k 下约 93ms）→ **改设置很快生效**，不用重建引擎。

### 4.1 一次处理，不是两次 ★★

**响度增益和音量增益先乘成一个系数，热路径只做一次乘法。**

★ 这不是"省一次循环"的优化，**两次处理在这件事上是错的**。三条理由，只有第三条是硬的：

**（一）热路径**：两次处理等于把逐样本循环跑两遍，内存流量翻倍。
192k/24bit 下这一趟本来只有约 0.4 ms/秒的 CPU —— **省它不是决定因素**。

**（二）精度**：现有代码是 `static_cast<int32_t>(...)`，**截断不是四舍五入**
（`audio_engine.cpp:648`）。两次处理截断两次，误差上限翻倍。
但这个误差 `< 1`（S32 整数域），而 `convertS32ToWire` 会右移 8 位输出 24bit ——
**误差整个落在被丢弃的低位里**。所以两次处理不会让精度差到听得出来。
**这条也别当理由。**

**（三）溢出 —— 这条才是真的，而且两次处理会造成不可逆的破坏**

`audio_engine.cpp:649` 上面那行注释白纸黑字写着：

> ★ 满量程是 ±2³¹，乘以 <=1 的增益不会溢出，不需要 clamp。

**这条推理建立在"增益 ≤ 1"上。响度增益可以 > 1**（要提升安静的歌），它当场失效。

两次处理的话，**第一次乘法（响度）就可能把样本顶出 ±2³¹**：

- C++ 里 `static_cast<int32_t>(float)` 超出范围是 **UB**
- arm64 的 `fcvtzs` 实际会**饱和**到 `INT_MAX` / `INT_MIN`
- **饱和之后第二次乘法（用户音量）再也救不回来** ——
  一个本该被音量压回去的峰值已经被削平了

具体例子：用户音量 −6dB、这首歌响度要 +5dB。

| | 第一步 | 第二步 | 结果 |
|---|---|---|---|
| 两次处理 | ×1.78 → **可能饱和** | ×0.5 | 峰值已被削平，救不回来 |
| 一次处理 | 先乘成 −1dB 的系数 | ×0.89 | **全程没有一步越界** |

**结论：顺序敏感的操作必须先合成系数。一次处理是正确性要求，不是优化。**

### 4.2 一次处理也免不了溢出 —— 真峰值钳制兜住它

用户音量停在 0dB、响度要 +5dB 时，合成系数 +5dB 照样能顶出范围。

保证来自**真峰值钳制**（见第八节）：

```
g = min(目标 − 响度, −真峰值 − 1dB)
```

这条保证 `|样本 × g| ≤ 2³¹ × 10^(−1/20) ≈ 0.89 × 2³¹` ——
**既不削顶，也永远不溢出 int32。**

★★ 所以第八节那个坑在这里**收第二次利息**：真峰值钳制不只是"保护 DAC"，
**它同时是让 S32 算术保持合法的那道保证**。少了它，热路径就是 UB。

**硬规则**：**只有同时拿到响度和真峰值，才允许 g > 1。**
缺任何一个 → 增益一律 ≤ 1。反正是同一趟测出来的，这条是兜底。

### 4.3 具体形状

```cpp
std::atomic<bool>  volumeEnabled_{false};
std::atomic<float> volumeGain_{1.0f};     // 用户音量，夹在 [kMinGain, 1.0]
std::atomic<float> loudnessGain_{1.0f};   // 响度，**不夹上限** ← 这就是 setGain 不能复用的原因
std::atomic<float> effectiveGain_{1.0f};  // = volumeGain_ × loudnessGain_，热路径只读这一个

void setVolumeGain(float g)   { volumeGain_.store(clamp01(g));  recomputeGain(); }
void setLoudnessGain(float g) { loudnessGain_.store(g);         recomputeGain(); }
```

★ **`applyGain` 的循环体一个字都不用改**，只把 `gain_` 换成 `effectiveGain_`。

★ **两个增益各存各的**（诊断报告要能分开显示"音量 −12 dB · 响度 −3.2 dB"），
但只把**乘积**交给热路径。

★ "0dB 跳过整个循环"那条承诺原样保住：合成系数 ≥ 1.0 才跳过 ——
也就是**音量和响度都为 0dB 时，一个样本都不碰**。

★ **不能复用 `setGain`**：`audio_engine.h:146-150` 把增益夹在 `[kMinGain, 1.0]`，
**只能衰减**。响度需要提升，所以要单独一个不夹上限的入口。
**音量滑条"只衰减"的语义必须保住** —— 设置页的上限/下限/锁（`Settings.kt:157-201`）
全建立在这个语义上，动了会连带出一串问题。

### 4.4 与音量控制的关系 —— 2026-10-17 p123 已解耦

**响度平衡与「音量控制」是两个独立开关，互不依赖。**

- **音量控制**是给“没有可用硬件音量的 USB 直连设备”准备的软件音量层；
  **响度平衡**是把曲目拉到同一基准的处理层。两者目的不同。
- 引擎里两层各有开关，合成系数 =（音量开？音量增益：1.0）×（响度开？响度增益：1.0）。
  - 音量关着、响度开着 → `applyGain` 仍要处理响度；
  - 两层都关或都停在 0dB → 合成系数 1.0，一个样本都不碰。
- `applyGain` **不再用 `volumeEnabled_` 当总闸**；真正的跳过条件是合成增益 == 1.0。
- `open()` 的位深提升条件改成 **`(volumeEnabled_ || loudnessEnabled_)`**。
- 播放页徽章**必须单独列「响度」**：以前“音量控制顺带摘掉 bit-perfect”的前提
  在解耦后不成立了。现在徽章会显示 `直通 · 音量 −12 dB · 响度 −3.2 dB` 这种组合。
- 两者的语义关系（用户 2026-10-17 定）：**响度先定基准，音量再做最终修正**。
  音量的上限/下限约束的是“最终修正”这一层，不约束响度基准本身。
- 音量层允许正向增益：**绝对范围 −80 ~ +15dB**（对齐 Adobe Audition 的推子范围），
  **默认上限仍是 0dB**，必须用户手动提高上限才会启用正增益。
  正增益是数字放大，不做自动限幅；推过头会在 0dBFS 削顶。
  引擎侧只保留满刻度饱和兜底（防止 int32 溢出），这不是限幅器。

### 4.5 ★ 换歌必须重新下发 —— 这是新增的必改点

**现在换歌不重下发增益。** `PlayerSession.playLocked()` 里没有任何
`nativeSetSoftwareVolume` 调用 —— 音量只在**句柄变化**时推一次
（切输出方式、拔插后 `setDevice` / `attachEngineOnly`）。
因为现在这个值在会话内是常量，不需要重推。

**响度增益是逐曲目的，所以必须新增一个下发点。**
而且**必须在打开文件之前** —— 否则起播预灌那一秒（`audio_engine.cpp:374-415`）
会用上一首的增益。交叉馈送当年踩的就是这个坑。

### 4.6 位深余量只对衰减有效

`audio_engine.cpp:160-163` 现在这么做：音量开着且源低于 24bit 时，
把输出位深提到 24bit —— 16bit 源左对齐到 32 位后低 8 位本来就是 0，
衰减先吃那 8 位空位，**−48 dB 以内不丢有效位**。

★ 但这个技巧**只对衰减有用**。提升是往满量程以上走，
**DAC 会削** —— 见第八节。这也是为什么真峰值钳制不能省。

### 4.7 DSD 不做 —— 明确排除，不是"暂时没做"

**范围就限定在通用 PCM 格式（flac / alac / wav / aac / mp3 / ape …），DSD 排除在外。**

两条理由，一条架构一条产品：

1. **架构上**：DSD 走原生位流，根本不经过 PCM 域（`decodeLoopDsd` 是另一条线程）。
   要测就得先把 DSD 降采样成 PCM，那是另一条完整的处理链。
   软件音量、交叉馈送都因为同一条理由对 DSD 无效。
2. **产品上**：DSD 用户要的就是"一个 bit 都不动"。给 DSD 加响度处理，
   和这个格式存在的意义直接冲突。

界面上对 DSD 曲目直接**不显示响度这一项**（不是显示"未测"）——
不显示才是明确的"这个格式不走这套"，显示"未测"反而像功能坏了。

## 五、测量从哪来

这是整个功能真正的工作量所在。三条路，**B 和 C 是主力，A 降级成可选**。

### A. 全库离线扫描

一次性把 2829 首全测一遍。问题：

- **必须整曲解码**。现在那次扫描（`media_probe.cpp:175-231`）只开文件头读标签，
  **一个解码器都不建** —— 这是两件完全不同量级的事。
- 成本：全库 **203.1 小时**音频（2026-10-17 实测，见附录）。
  **真机实测中位 462 倍实时** → 全库约 **30 分钟**（加权估，见附录）。
- 得做成可中断、可续跑的后台任务，还要有进度界面。
  `CoverDedupe.schedule()`（`CoverDedupe.kt:92-108`）是现成的模板。

**结论：30 分钟，不再是"太重"。** 但作为主路径仍然不必要 ——
B + C 已经能覆盖"用户实际在听的"，A 留作"把整个库一次性统一"的可选动作。

★ 这条一开始按"1~3 小时"估的，实测下来是 **30 分钟**，差了一个数量级。
原因是估算时想当然地以为"成本 ≈ 解码成本"，
**实测下来解码只占 8~12%，其余全是分析本身**（见附录）。

### ★ 2026-10-17 实现偏离：不做 C（解码热路径 tap）

**实际实现没有在播放解码线程里挂测量器**，而是统一走独立分析线程：

- 当前曲目在起播前由分析线程单独解码测一遍（最多等 3 秒）；
- 下一首/当前专辑/队列在后台继续测；
- 好处是**完全不碰实时解码路径**（实时线程三条铁律：无 I/O、无重分配、
  不额外抢 CPU），也不需要处理 seek 让测量失效的判据。
- 代价是每首多解码一次：实测中位 0.56 秒、最慢 2.22 秒，
  而且每首只测一次。对"避免播放卡顿"的目标来说这个取舍更稳。

所以下面 C 的描述只作为历史方案保留；**实现以本节的独立分析线程为准**。

### B. 预分析下一首 ★

**播当前这首的同时，在后台把下一首测掉。**

时间预算非常宽裕：一首 4.3 分钟的歌给 260 秒墙钟，
而实测测一首**中位 0.56 秒、最慢 2.2 秒**（见附录）。**余量 100 倍以上**，
多预分析两三首都放得下。

- 覆盖**顺序播放**（专辑、歌单）—— 播到下一首时增益已经就绪，从第一个样本就正确。
- 随机播放预测不了 —— 只能退化成"播到了再测"（见 C）。
- 实现上**另开一个解码器**读文件，不去动播放那条流：
  播放流经过重采样和交叉馈送，**测的必须是源，不是处理后的信号**。

### C. 顺带测当前这首 ★★

解码循环手里本来就有**源 PCM**（`srcBuf`，重采样之前，`audio_engine.cpp:395-400`）。
把这些帧喂给 K 加权 + 分块累加器，成本约 **0.2%（44.1k）/ 0.7%（192k）CPU**
（实测分析段 382 ms 处理 200 秒音频折算），**零额外 I/O、零额外解码器**。

也就是说：**你听过的每一首歌，都是免费测出来的。**

代价是**结果要到这首歌播完才落地** —— 所以它从**第二次听**开始才起作用。

### 5.1 为什么不能"边播边测、当场生效"

★★ **集成响度是一个"全曲属性"。** BS.1770 的集成值定义在整个节目上
（400 ms 分块 + 两级门限的统计量），**这首歌没播完，这个数就不存在**。

所以"播着这首歌、同时算出这首歌的响度、然后立刻用上" ——
**数学上做不到**。任何声称做到的实现，用的都不是集成响度
（要么是短时响度、要么是峰值，那是别的东西）。

这正是 B 和 C 要分工的原因：

| | 覆盖谁 | 什么时候生效 | 额外成本 |
|---|---|---|---|
| **C. tap 当前** | 我**听过**的 | 从**第二次**听开始 | ≈0.2~0.7% CPU |
| **B. 预分析下一首** | 我**马上要听**的 | 从**第一个样本**开始 | 每首 0.56 秒（中位） |
| A. 全库扫描 | 剩下的全部 | 扫完就有 | 全库约 30 分钟 |

B + C 合起来，**"你实际在听的音乐"几乎总是已经测好的**，
而且用户完全感知不到有这个功能在跑 —— 没有进度条、没有等待。

### 5.2 第一次播放怎么办 —— 可以等，但要封顶

遇到一首**从没测过**的歌，两条路：

| | 做法 | 体验 |
|---|---|---|
| **先测再播** ★ | 分析完再起播，界面上显示"分析中" | 首曲就正确，代价是等一下 |
| 先播再测 | 原样播，播完落盘，下次才对 | 不等，但这一首没归一化 |

**决定走"先测再播"**，因为实测等得起：中位 **0.56 秒**、最慢 **2.2 秒**
（见附录）。0.5 秒的等待用户基本感觉不到，2 秒也远好于"这首响度不对"。

★★ **但必须封顶。** 那个 0.56 秒是**空载**测出来的：单线程、没别的事在跑。
真机上可能同时在放音乐、后台有别的 App，而且调度器会把人扔到小核上
（实测见过同一段代码差 6 倍）。超长曲目（>15 分钟）本身也会超 5 秒。

#### 规则：墙钟计时器，3 秒到点就走 ★★

**不按曲目长度估，也不按"我这台手机测出来的倍速"估** ——
这个 App 是要发出去的，别人的手机可能慢两三倍，超长曲目本来也更久。
估算出来的阈值必然有一边是错的。

所以：**一个跟设备无关的墙钟截止时刻。**

```
用户点下播放那一刻  t0 = SystemClock.elapsedRealtime()
                    deadline = t0 + 3000
```

★ **计时起点是"用户点下播放"，不是"分析器开始跑"** ——
开文件、建解码器、解码、分析，全都算在这 3 秒里。用户感受到的就是这 3 秒。

★ **不另起 timer 线程**：工作线程每解一段（比如每 64 帧）看一眼
`elapsedRealtime() > deadline`，超了就自己收尾。多一个线程只会多一处竞态。

#### 状态机

| 时刻 | 发生什么 |
|---|---|
| **① 分析在 3 秒内完成** | 算出增益 → 下发 → 开文件起播。**从第一个样本就是对的**（绝大多数情况） |
| **② 3 秒到点还没完成** | **立刻起播，增益 1.0**；分析**继续跑**（不杀） |
| **③ 分析在播放中途完成** | 结果落盘；**把增益斜坡套上去**（见下） |

★ ② 里分析不能杀 —— 它已经跑了一大半，杀掉等于白费，而且用户还得再等一次。

#### ③ 那次增益跳变必须做成斜坡 ★

超时之后，歌已经在放了，增益才到达。直接一步跳过去，10 dB 的话就是**一声明显的电平跳变**。

所以要做成**淡入**：`applyGain` 内部保留一个"当前增益"，每个块朝"目标增益"走一步，
约 **250 ms** 走完。

★ 这个斜坡顺带修好一个既有问题：**拖动音量滑条时，增益也是按块（约 93 ms）跳变的**，
调得急会有拉链声。加了斜坡之后，音量滑条也变得顺了。
代价是音量响应慢了 250 ms —— 感觉不出来，但换来的是没有台阶。

★ **它不改变"增益 == 1.0 就跳过整个循环"那条承诺**：目标为 1.0 且当前已到 1.0 时，
照样一个样本都不碰。

#### 超时必须可取消

换歌、返回、退出播放页 → 正在跑的分析要能**立刻中断**，不能占着 CPU 跟新歌的分析抢。
FFmpeg 的解码循环每包查一次取消标志即可。

#### 这条规则的代价，要认下来

★ **慢设备上，每一首没测过的歌都会等满 3 秒。** 这是有意的、可预测的 ——
比"有时等 0.5 秒、有时等 8 秒"好。而且它只发生一次：测过的歌永久在 `loudness.json` 里。

★ **B（预分析下一首）能极大减少这种情况** —— 顺序播放时后面的歌早就测好了，
只有"这个会话的第一首"可能撞上。所以这个 3 秒上限是**兜底**，不是常态。

★ **不要用"猜"的兜底**（比如拿专辑平均值顶替）。
猜错了比不做好，而且用户无从判断。

## 七、怎么应用：单曲 + 专辑，以及"什么才算一张专辑"

```
增益(dB) = 目标响度 − 实测响度
增益(dB) = min(增益, −真峰值 − 1dB)     ← 见下节，这一行不能省
```

### 7.1 两种模式

- **单曲模式**（ReplayGain track）：每首各自归一化。
  换歌时响度一致，但**同一张专辑内部的强弱对比会被抹平**。
- **专辑模式**（ReplayGain album / R128 album）：整张专辑当一个节目测
  （把所有曲目的分块能量并到一起，**只门限一次**），全专辑共用一个增益。
  **保住专辑内部的动态**，这是更"发烧"的做法。

### 7.2 怎么判定"什么才算一张专辑" ★★

**问题**：歌单批量下载会把几十上百首歌塞进一个"专辑"里。
本项目实测（2026-10-17，见附录）：

```
WYY        1325 首 / 96.0 小时 / 285 个不同歌手   ← 歌单转存，不是专辑
第二大      74 首（"2013 陈奕迅 Music Life 精选"）
其余       6~12 首的正常专辑 52 个
```

把 1325 首当成一个"节目"去测，等于拿 96 小时的平均响度去套每一首歌 ——
毫无意义，而且比不做还糟。

**规则**：

> **一张专辑的曲目数 < 50 → 用专辑模式；≥ 50 → 退化成单曲模式。**

实测这个阈值在本库上很好用，因为 **74 和 1325 之间是断崖**，中间一首都没有：

| 阈值 | 按专辑做 | 按单曲做 |
|---|---|---|
| < 50 首 | 180 个专辑 / 1430 首（51%） | 2 个：WYY(1325) + 74 首精选 |
| < 80 首 | 181 个专辑 / 1504 首（53%） | 1 个：WYY(1325) |

★ 50 这条线顺带把那个 **74 首的"精选"也划进单曲** —— **这是对的**：
精选是从不同年代、不同母带拼出来的，本来就不该共用一个增益。

★ "一张专辑"沿用**现有的分组**（`Library.albums()` / `albumKeyOf`：
优先 album 标签，标签空则回落文件夹名），不要另建一套判定。
两套分组不一致时，用户会在专辑页看到一张专辑、播放时却按另一个口径归一化。

★ 沿用现有分组还有个副作用要认下来：**两张同名专辑会被并成一张**
（比如两个版本的 "Greatest Hits"）。专辑页现在就是这么合并的，
响度也跟着合并没有问题 —— 但**别一边合并、一边又按目录分开算**。
增益的索引键就用专辑名，和专辑页看到的完全一致。

### 7.3 模式设置

给三档，默认第一档：

- **自动**（默认）—— 按 7.2 的规则逐张判定
- **全部单曲** —— 有人就是喜欢每首一样响，包括专辑内部
- **全部专辑** —— 完全尊重专辑，大杂烩也当专辑（不推荐，但要给）

### 7.4 专辑模式的一个固有代价

★ 专辑增益要**整张测完**才存在。一张 44 首的专辑，测完约 1 分钟 CPU，
而第 1 首只给你 4 分钟的墙钟 —— **来得及测完，但赶不上第 1 首开头**。

所以：**一张从没测过的专辑，第一次播的时候第 1 首（可能还有第 2 首）
是原样播的**，之后才套上专辑增益。第二次听就完全正常。

自愈的，接受它。不要为了"从第 1 首就正确"而卡住播放等分析 ——
那是拿确定的等待换一个不确定的收益。

### 7.5 界面

界面上应该能看见当前这首**实际用了多少增益**（比如"响度 −3.2 dB"），
以及这一首是按单曲还是按专辑归一的。
不然用户没法判断它到底干了什么，也没法判断"这张专辑怎么忽大忽小"是不是 bug。

## 八、真峰值与削顶 —— 这一节是坑

★ **归一化到某个目标，意味着安静的歌要被"提"起来。**

而"安静"和"峰值低"是两回事：

- 现代流行：又响又平（母带压得很狠）→ 归一化时**衰减**，安全。
- 老录音、古典、爵士：**安静但峰值很高**（真实动态大）→ 归一化时**提升**，
  **一提就削顶**。

不做真峰值保护的后果是：**这个功能会专门毁掉你库里最该被善待的那部分音乐。**

所以：

1. 必须同时测**真峰值**（EBU Tech 3341，4 倍过采样），B/C 那两趟顺手就算。
2. 增益取 `min(目标−响度, −真峰值−1dB)`，那个 1 dB 就是 R128 建议的 −1 dBTP。
3. 代价是：峰值高的歌提不满，会**略轻一点**。这是正确的取舍 ——
   宁可轻一点，也不要削顶。

**不建议加限幅器（limiter）** —— 那是又一次改样本，而且会引入自己的失真。
归一化本身已经是一次"改样本"了，别再叠。

## 九、风险与约束

### 9.1 CPU 抢占 —— 这个项目在这上面栽过

`thread_priority.h` 的文件头写得很清楚：

> 实测一次切屏能让解码线程停摆 **1 秒以上** —— 缓冲耗尽后就是一段可闻的静音。

所以分析线程：

- 优先级必须是**低**的（正 nice 值），和 USB 提交（−19）、解码（−16）拉开档次。
  `PrioritySlot` 现在是 `kSlotCount = 2`，加第三个槽是顺手的事。
- **要在播放确实健康的时候才跑**：环形缓冲水位低于目标水位、或者刚发生过
  underrun 时，分析暂停。宁可慢慢测，也不要出爆音。

### 9.2 seek 会让测量不完整

C（tap 当前）只看到了**实际播过的那部分**。用户从中间开始播、或者中途 seek，
拿到的就不是整曲集成响度。

★ 规则：**只有"从头完整播到尾、中途没 seek"的结果才落盘**。
判据现成 —— `seekCount_`（`audio_engine.h:238`）。
不完整的测量直接丢掉，交给 B 或下次播放重测。

### 9.3 随机播放预测不了

B 在 shuffle 下没有"下一首"可言。退化成"播到了才测"，
也就是那一首第一次听不归一化。

★ 队列页可以显示"已测/未测"，让用户自己决定要不要跑一次全库扫描补上。

### 9.4 开了就不是 bit-perfect

**默认关，独立开关**（2026-10-17 p123 解耦，不再依附音量控制）。

★ 音量控制或响度平衡**任一层开启**都不再适用 bit-perfect；播放页徽章分别列出
「音量」「响度」，不会再出现“只开了响度却还写直通 · bit-perfect”的错误。

★ 设置页两张卡片各自明说自己的影响，用户有权知道每一层在做什么。

### 9.5 硬件音量路线：考虑过，不用

`nativeSetVolume` 是设备的 UAC 硬件音量，**不碰样本、保持 bit-perfect**，
而且它天然只能衰减（DAC 的衰减器），**结构上不可能削顶** ——
单看技术，这是"响度平衡"最干净的实现。

**但决定不走这条路**，两条理由：

1. **产品上**：响度平衡定义为一个**独立的软件处理层**（4.4，2026-10-17 与音量控制解耦），
   不引入第二套音量通路。多一条通路就多一套状态、多一组组合规则、
   多一片"为什么这台设备有这个开关那台没有"的解释成本。
2. **这台设备本来就不支持**。`docs/10-开发日志.md:669` 起有实测：
   Dawn Pro 的固件在描述符里声明了 Volume 能力（`bmaControls[0]=0x0F`），
   但对 SET_CUR / GET_CUR 一律返回退化范围 `min=1 / max=0 / res=0`，
   三个通道号返回**完全相同的字节** —— 它根本没在看请求。

★ 代码里那套能力探测（`nativeVolumeRange` / `nativeVolumeProbe`）**保持原样别动** ——
它现在只挂在诊断页，将来遇到支持的设备还有用。只是响度平衡不接它。

★ 界面上两者别摆一起：一个是"设备级音量"，一个是"软件级响度处理"，
混在一张卡片里会让人以为是一回事。

## 十一、考虑过但没选的

记在这里，免得以后有人重新想一遍。**理由比结论重要。**

| 方案 | 为什么不用 |
|---|---|
| **走 UAC 硬件音量** | 技术上最干净（不碰样本、天然不削顶），但**决定不走**：响度平衡定义为音量控制下的软件层，不引入第二套音量通路。而且本机设备实测不支持（见 9.5） |
| **只衰减（软件域）** | 结构上不可能削顶、不需要真峰值，但目标只能取"当前上下文里最响的那首"→ **加进一首特别响的歌，整个基准会跟着往下移**，目标不稳定 |
| **限幅器**（Spotify 走这条） | 允许提满、只在峰值上削一下，但**引入限幅器自己的失真**。这个项目的用户对"引入失真"的容忍度明显低于对"某几首轻一点"的容忍度 |
| **动态响度控制 / AGC** | 压动态，和"bit-perfect 直通"的气质正相反（第二节） |
| **EBU R128 的 dynamic 模式** | 属于 AGC 那一类，广播用的 |
| **峰值归一化 / RMS 归一化** | BS.1770 就是为了取代它们才有的 |
| **目标取曲库中位数** | "大部分歌几乎不动"很有吸引力，但目标不再是绝对值，换库换设备不通用。可以将来做成"自动"档，现在不做 |
| **把增益写回文件标签** | ReplayGain 原本的设计，能让别的播放器也认。但**这个项目绝不能碰用户的音乐文件** |
| **队列内相对归一化** | 不可预测，同一个文件在不同队列里表现不同 |

>    （0.5 LU 输入）。改目标**只重算增益，不重新测量**。
> 3. **A 全库扫描**：**保留**，打开开关即入队；播放开始时 P0/P1/P2 抢占，
>    全库 P3 让路，播放结束后继续。
> 4. **失效判据**：`size + mtime + algo`。`loudness.json` 里带 `version` 和 `algo`，
>    算法实现改了就把旧结果整体作废。
> 5. **专辑上限**：**给用户调**，数字输入，默认 50，范围 2 ~ 500。
> 6. **显示**：分开显示。正在播放页一行「响度 −3.2 dB · 专辑 · 峰值限制」，
>    「源」面板和会话日志里另有目标/实测/真峰值；音量仍在原有位置。
> 7. **增益斜坡**：**250 ms**，逐样本线性；目标==当前==0dB 时仍然整段跳过。
> 8. **真峰值**：**总是测、总是存**。理由：目标随时可能调高，
>    只对衰减曲目省掉真峰值会让"改目标零成本"失效；而且真峰值也是
>    保证 S32 热路径不溢出的硬前提。
>
> **额外定稿：**
> - 模式只保留 **自动 / 全部单曲** 两档（砍掉"全部专辑"）。
> - 自动模式：专辑曲目数 **少于** 用户设的上限才按专辑；上限最大 500。
> - 调度：P0 当前曲目 → P1 当前专辑 → P2 队列下一批 → P3 全库。
>   当前曲目的单曲值只作为**起播桥**，专辑结果到达后 250ms 斜坡切过去。
> - 实现：独立分析线程，**不碰播放解码热路径**（见第五节开头的 2026-10-17 说明）。
> - 真峰值滤波器：当前是 4× 过采样 + Blackman 窗 sinc 近似，
>   与 ffmpeg ebur128 实测误差 <0.1dB；标准 48 抽头系数留作 Phase 2 精度项。
>
> 原始待确认项保留在下面，作为背景记录。

1. **测量内核**：自己写 BS.1770（约 250 行 C++，无新依赖、不涨体积）
   还是把 libavfilter 加进 FFmpeg 构建（`CMakeLists.txt` 现在只链了
   `avcodec / avformat / avutil / swresample`，没有 libavfilter；加进去产物大 2~3 MB）。
   —— 倾向自己写：这个项目连 UAC 协议栈和 DSD 解析都是自己撸的。
2. **目标响度**：−14（流媒体）/ −16（Apple）/ −18（ReplayGain 2.0 官方值）？
   还是做成可选（建议可配，默认 −18）？
3. **要不要保留 A（全库离线扫描）**，还是先只做 B + C？
4. **`loudness.json` 的失效判据**除了 size+mtime 还要不要别的
   （比如把测量算法版本写进去 —— 算法改了旧值就该作废）？
5. **50 这个阈值要不要给用户调**，还是写死？
   —— 建议写死：实测本库 74 和 1325 之间是断崖，可调只会多一个调错的入口。
6. **诊断报告/徽章怎么显示两个增益**：分开显示"音量 −12 dB · 响度 −3.2 dB"，
   还是只显示合成后的总增益？—— 建议分开，用户要能判断响度到底干了什么。
7. **增益斜坡时长**：建议 250 ms（5.2 第 ③ 条）。太短还是会有台阶感，
   太长会让人觉得音量"跟不上手"。
8. **要不要做"需要提升时才补算真峰值"的优化**：真峰值占总耗时 30%，
   而它只在**要提升**时才有用 —— 衰减时完全不需要。
   实测样本里 12/20 首在 −18 LUFS 目标下是衰减，可以省掉那一趟。
   代价是要多一个"真峰值未知"的状态位。

### 专辑规模分布（182 个专辑标签）

| 曲目数 | 专辑个数 | 曲目数 |
|---|---|---|
| 1 | 68 | 68 |
| 2–5 | 22 | 79 |

★ **74 和 1325 之间是断崖，中间一首都没有。** 7.2 那个 50 的阈值就是照这个定的。

### WYY —— 为什么需要 7.2 那条规则

```
曲目数    1325 首（占全库 46.8%）
总时长    96.0 小时
歌手数    285 个不同 artist
目录      全部在 WYY/ 一个文件夹下

前几名：Eagles 154 / Justin Bieber 148 / Maroon 5 93 / Goose house 68 /
        Charlie Puth 43 / Coldplay 41 / VISUAL ARTS 32 / Chris James 27
```

**285 个歌手塞在一个"专辑"里 —— 这是歌单转存，不是专辑。**
按专辑模式处理它，等于拿 96 小时的平均响度去套每一首歌。

### 三条推论

- **99.3% 是 ALAC** → "先读文件里已有的 ReplayGain / R128 标签"这条捷径
  对这个库帮助有限：iTunes 系通常不往文件里写这类标签（它写在 iTunes 数据库里）。
  留着当"有就用、没有才测"还行，但不能当主路径。
- 采样率跨度 44.1k ~ 192k，**K 加权系数必须按采样率重算**（见 3.1），
  不能只按 48 kHz 的系数算。
- **WYY 占掉 46.8% 的曲目和 47% 的时长** —— 它是这个库里最大的一块，
  7.2 那条规则不是边角情况，是主路径。

## 附录二：真机实测（2026-10-17）

### 怎么测的

`tools/loudness_bench.cpp` —— 一次性实验工具，**不进 App**。
用 NDK 交叉编译成 arm64，连同项目自己的 FFmpeg `.so` 推到手机
`/data/local/tmp/lb/`，**在手机上跑**，读的是手机内部存储里的曲目。

设备：`23013RK75C`（SoC `taro`），aarch64，NDK r27。

处理链和将来要实现的一致：解码 → 转 float → K 加权 → 400ms/75% 分块
→ 两级门限 → 集成响度，外加真峰值（4 倍过采样）。

★ 两处比真实实现**偏慢**：这里用 `libswresample` 转 float，
真实现里引擎手里已经是「左对齐 S32」，不需要 swr。

### 数值验证：和 ffmpeg 的 `ebur128` 对拍

| 曲目 | 本工具 | `ffmpeg -filter_complex ebur128` |
|---|---|---|
| Metrocity | −8.16 LUFS | **−8.2 LUFS** |
| Solti 贝九第四乐章 | −14.10 LUFS | **−14.1 LUFS** |
| 真峰值 | −0.07 / −0.11 dBFS | −0.1 / −0.0 dBFS |

**对上了**（ffmpeg 只印一位小数），K 加权和门限的实现是对的。

### 耗时：随机抽 20 首

```
单曲耗时    中位 587 ms   平均 762 ms   最慢 2057 ms
倍速        中位 462x     最慢 116x
折算成 4.3 分钟标准曲长：中位 0.56 s   最慢 2.22 s
```

★ 最慢的几首全是高采样率的（116x = 192k，221x = 96k）——
分析成本随采样率线性涨。

★ **全库折算**：按曲库的采样率构成加权（44.1k 74% / 48k 11% / 96k 11% / 192k 3%）
得约 420x → 203.1 小时音频 / 420 ≈ **29 分钟**。

### 耗时拆解（200 秒的 44.1k ALAC，跑 4 遍）

```
带真峰值   总 422/437/436/425 ms     分析 374~386 ms
不带真峰值 总 301/278/314/311 ms     分析  86~97 ms
```

**真峰值占约 30% 的总时间。**

★★ 但**分段拆解不可信**：跳过真峰值时，"解码"那段从 35 ms 涨到 190 ms ——
复现的。原因是真峰值那段是长而密的计算循环，把 CPU 频率顶在高位；
去掉它之后代码变成"短解码 + 短分析 + 等 I/O"，调度器看到空隙就把频率降下来了。
**只有总耗时可信。**

★ 另一条教训：同一份代码两次跑能差 6 倍（安卓调度器决定落在哪个核上）。
**单次测量没有意义**，这个数必须多跑几遍。

### 顺带撞出来的两件事

**一、响度跨度 25.1 LU**

20 首随机样本：最响 **−6.42 LUFS**，中位 **−15.31**，最轻 **−31.56**。

这是这个功能存在意义的直接证据 —— 25 dB 的跨度，正是"听歌单要不停摸音量键"的原因。

**二、6/20 首的真峰值超过 0 dBFS**

```
+0.34  +0.23  +0.21  +0.13  +0.06  +0.03  dBFS
```

这些文件的**采样峰值**按定义不可能超过 0 dBFS（它们是合法 PCM），
但重建出来的波形超了 —— 这就是 inter-sample peak。

★ 如果按"采样峰值"来钳制增益，这 6 首会直接削顶。
**真峰值测量不是可选项，第八节那条规则是硬的。**
