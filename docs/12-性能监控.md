# 性能监控与日志（p127）

> 目标：出问题时能回答“慢在哪、为什么慢”，而不是靠猜。  
> 原则：**播放/解码线程绝不做日志 I/O**；正式版默认关闭。

---

## 1. 为什么单独做

p125 的实机日志显示：自动切歌时，从 `▶ 曲目` 到 `响度平衡` 之间有 **3.7 秒**空档，
但整段日志里 **没有** `响度分析中…`。这说明它不是 `ensureTrack(3000)` 在等，
而是播放路径里某一段（文件打开、分析器锁、`decide`、JNI/设备）在耗时间。

原来的日志只有“开始/结束”这种粗粒度事件，无法定位到具体阶段。
所以增加 `PerfTrace` + `LoudnessAnalyzer.snapshot()`。

---

## 2. PerfTrace 的线程模型

```
播放/分析线程
   └─ PerfTrace.mark / span  →  有界队列（offer，非阻塞）
                                      ↓
                             perf-writer 线程（单条，daemon）
                                      ↓
                    files/logs/perf-YYYYMMDD.log + logcat (HiFiPerf)
```

约束：

- 队列容量 4096；满了丢事件并累加 `dropped`，**绝不阻塞调用方**。
- writer 线程每 1 秒 flush 一次；文件按天/8MB 轮转。
- 最近 512 条事件同时保留在内存环形缓冲，供诊断页/导出报告读取。
- 关闭时 `mark/span` 直接返回，不启动线程、不创建目录。

### 开关

- debug 构建（`FLAG_DEBUGGABLE`）默认开启；
- release 默认关闭；
- 需要现场排查时，可通过现有调试开关打开。

## 3. 已埋点

### 播放路径（PlayerSession）

| span / mark | 含义 |
|---|---|
| `play.begin` | 开始一次切歌 |
| `play.close` | 收掉上一个会话 |
| `play.fd.open` | 打开文件 fd |
| `play.fd.detach` | detachFd |
| `play.outputMode` | 下发输出模式 |
| `play.loudness.start` | 启动分析器 |
| `play.loudness.prioritize` | 入队/提权当前曲目、专辑、后续 3 首 |
| `play.loudness.decide` | 读缓存并算增益 |
| `play.loudness.cache` | 命中/未命中、key、size/mtime |
| `play.loudness.ensure` | 起播前等待分析（应有上限 3 秒） |
| `play.loudness.apply` | 把增益推给引擎 |
| `play.nativeOpen` | 原生打开文件/解码器 |
| `play.device` | 选 alt / claim / SET_CUR / 启动 |
| `play.total` | 整次切歌总耗时 |

### 分析器（LoudnessAnalyzer）

| 事件 | 含义 |
|---|---|
| `analyzer.job.start/end` | 任务开始/结束，含 key、专辑/单曲、优先级、总耗时 |
| `analyzer.track` | 单首耗时、成功/失败、LUFS |
| `analyzer.job.abort` | 被取消/被抢占 |
| `analyzer.job.error` | 未捕获异常 |
| `analyzer.preempt` | 高优先级任务抢占 |
| `analyzer.ensure.enter/exit` | 起播等待的入口/出口与实际耗时 |

### 缓存

`LoudnessStore.describe(track)` 会给出：

```text
hit:lufs=-10.09 tp=-11.83 key=...
miss:no-entry key=...
miss:meta key=... stored=size/mtime current=size/mtime
```

## 4. 队列明细 / 处理时间 / 处理模式

`LoudnessAnalyzer.snapshot()` 提供只读快照，UI 1.5 秒刷新一次：

- **模式**：自动 / 全部单曲；当前任务是专辑还是单曲；
- **优先级**：P0 当前曲目、P1 当前专辑、P2 队列、P3 全库；
- **当前任务**：曲目/专辑、`done/total`、已用时间、排队时间；
- **下一批**：按优先级列前 10 项；
- **耗时**：单曲/专辑的最近、平均、最慢；
- **累计**：完成、失败、抢占；
- **缓存**：曲目/专辑数量。

展示位置：

- 设置页 → 响度平衡 → 后台分析（明细 TextView）；
- 诊断页 → 响度分析监控（实时刷新）；
- 导出报告 → `[响度分析监控]` 与 `[性能埋点]` 两节；
- `files/logs/perf-*.log` / logcat `HiFiPerf`。

---

## 5. 使用建议

1. 复现一次卡顿；
2. 看 `play.total` 与各 span：最大的一段就是瓶颈；
3. 看 `play.loudness.cache`：确认是命中缓存还是 `miss:meta`；
4. 若 `play.loudness.ensure` 接近 3000ms，查分析器抢占/任务队列；
5. 若 `play.fd.open` 很大，查存储/FUSE/文件本身；
6. 若 `play.device` 很大，查 UAC claim/alt/SET_CUR。

正式版发布时监控默认关闭；发布前确认 `PerfTrace.enabled == false`，不需要保留日志线程。

## p128：专辑分组缓存

p127 日志确认切歌停顿来自 `Library.albumOf()`：
`prioritizeForPlayback` 最多调 4 次，`decide`/`apply` 再各调一次；
每次 `albums()` 都遍历全库重建分组（2829 首约 550ms），合计 3–5 秒。

p128 把 `albums / albumByKey / albumByUri` 放进 `Library.Snap`，
只在 `replaceTracks()` 时重建；`albums()` 直接返回缓存，
`albumOf()` 先按 uri 查、再按专辑键兜底，变成 O(1)。
播放路径不再做整库分组，`play.loudness.*` 的耗时应在个位数毫秒。
